# 豆包工作：桌面Agent与飞书协作工作台

## 它是什么

豆包工作是一类以“目标执行”为中心的桌面 Agent 工作台。

与普通问答型聊天工具相比，它更适合处理本地文件、浏览器任务、文档与表格、多步骤调研、代码与数据处理、图片 / 视频生产、外部连接器、可复用 Skill、长任务与批量任务。

用户提供的两篇 2026-10-01 / 10-02 实操教程都把它和普通豆包 App 区分开：

```text
普通聊天：问一句 → 答一句

工作型 Agent：
给目标
→ 读材料
→ 拆步骤
→ 调工具
→ 生成 / 修改文件
→ 校验
→ 把结果落到长期可用的文档、表格或本地文件
```

长期值得关注的不是“豆包工作一定比谁强”，而是这种**结果落地型 Agent 工作方式**。

官方入口：https://www.doubao.com/work

> 功能、模型、价格、配额和入口变化很快。本页保留长期工作方式；具体版本信息在真正使用前以官方客户端为准。

---

## 一、最重要的能力：让结果落到可继续工作的载体

聊天框里的回答很容易变成一次性信息。更有价值的是让输出进入 Markdown / 文档、表格、飞书文档、飞书多维表格、本地项目文件或可继续编辑的工程文件。

这意味着下一轮任务可以搜索、排序、筛选、批量处理、继续修改并复用历史结果。

因此评价这类工具时，不要只问“模型答得聪不聪明”，还要问：

> 它能不能把结果变成可管理、可验证、可继续加工的资产？

---

## 二、本地电脑与云电脑：先选执行环境

### 本地电脑

适合读取本机文件、修改本地项目、处理大文件、运行本机工具，以及使用已经安装在本机的 CLI、依赖或 Skill。

主要代价是电脑要保持运行、权限范围必须自己控制、性能受本机影响。

### 云电脑

适合纯联网调研、长时间任务、不需要本地文件的执行，以及需要关闭个人电脑后继续运行的工作。

主要边界是云环境与本地环境通常隔离；临时沙箱可能被回收；云端安装的依赖、登录状态和 Skill 不应假设永久保留。

长期原则：

> **涉及本地资产时优先本地；只依赖网络且运行时间长时可以考虑云端。**

---

## 三、项目：把长期上下文放进一个工作区

长期任务最好不要每次重新上传规则、参考文件、项目背景和历史成果。

项目机制的价值在于让同一工作区里的材料持续成为后续任务背景：

```text
一次性对话 → 临时答案
项目 → 连续上下文
仓库 / 文档资产 → 跨会话长期事实基准
```

项目仍然不能替代明确的版本、文件和事实来源。重要任务依然应该指明当前基准文件、需要修改什么、哪些内容不能覆盖、交付标准是什么。

---

## 四、计划模式与目标模式：分别控制开工前和交付前

两篇教程中比较值得长期保留的，是“计划”和“验收”分离。

### 计划模式

用途是高返工成本任务先看计划，再允许执行。适合修改文件、编程、大型报告、PPT、多步骤跨工具任务，以及用户自己还没有完全想清楚的复杂任务。

理想流程：

```text
读取材料
→ 给实施计划
→ 用户修改 / 批准
→ 再执行
```

它解决的是：**别让错误方向先跑完整套执行。**

### 目标模式

用途是把硬性验收条件前置，让 Agent 在交付前自己逐项检查。适合每个文件都必须产出对应结果、报告必须覆盖若干条要求、多个子文档缺一不可，或任何可以写成明确检查清单的任务。

理想流程：

```text
定义目标
→ 执行
→ 自动逐项验收
→ 不达标就返工
→ 全部通过再交付
```

这两个思想不依赖豆包工作本身，对应更普遍的 Agent 设计：

```text
Plan Gate：控制“是否按这个方向开工”
Acceptance Loop：控制“是否真的达到交付标准”
```

---

## 五、权限控制：高风险动作不要默认全放开

用户教程提供了“始终询问 / 按需确认 / 全部允许”一类权限思路。长期更重要的是：

> Agent 的权限应与任务风险匹配。

建议：读取可以相对宽松；写文件要限制目录；删除、覆盖、发送、邀请、发布、支付等操作提高确认等级；外部连接器只继承用户本来就拥有的权限；不要把整个硬盘、整个云盘或全部企业空间当作默认工作区。

处理本地文件时，一个好习惯是：**单独创建任务目录，只授权必要范围。**

## 六、Skill、连接器和角色是三种不同扩展

### Skill：怎么做

保存稳定流程、工具调用、脚本、检查清单和专项方法。

### 连接器：能访问什么

负责与 GitHub、飞书、Google Drive、Gmail、广告平台、企业系统等外部服务连接。连接成功不等于拥有全部权限。

### 角色 / 工作伙伴：谁负责

按数据分析、调研、写作、PPT、运营等职责组织 Agent。

长期不要把三者混成一个概念：

```text
角色 = 谁承担
Skill = 怎样执行
连接器 = 能访问哪些外部系统
```

## 七、批量与队列：适合把重复工作交给 Agent

任务队列的真正价值是：在当前任务运行时继续排后续任务、把同类任务批处理、降低人工等待和反复接力，并在出现错误时允许插入纠偏。

适合多文件整理、周期性报告、批量转换、同一数据集的连续加工，以及多个独立但相似的内容任务。

但任务能否排队，不等于任务应该无限并行。依赖同一文件、同一账号状态或前后步骤的任务，仍需保证顺序与锁定。

---

## 八、文档、表格、图片和视频：先定义交付，再选能力

两篇教程列举了大量具体功能。更稳定的使用方法不是背功能菜单，而是先定义：谁使用、最终文件是什么、需要哪些字段或章节、哪些内容必须来自材料、哪些步骤要人工确认。

文档适合生成、改写、格式转换、拆分合并、结构化抽取与翻译；表格更适合批量数据、排序、筛选、去重、统计和长期积累。

图片 / 视频真正影响结果的通常不是“点哪个按钮”，而是输入素材质量、参考图、脚本、镜头设计、时间轴、画风一致性和返工粒度。

模型名称和能力边界变化很快，因此本页不把 2026-10-01 / 10-02 的具体模型版本、价格和生成时长作为长期规则固化。

## 九、一个高价值实操：公开短视频数据 → 结构化素材库

其中一篇教程完整展示了一个很有代表性的 Agent 工作流：

```text
公开博主主页
↓
真实浏览器获取作品列表
↓
逐条进入详情页
↓
采集标题、文案、互动数据、日期
↓
获取完整逐字稿
↓
AI 生成主题标签和主题总结
↓
写入飞书多维表格 / 本地 Markdown
↓
去重与质量验证
```

它真正值得长期保留的，不是“扒抖音”本身，而是**批量公开信息采集的质量控制方法**。

### 1. 明确输入

至少明确来源 URL、数量、是否需要完整逐字稿、结果写到哪里。

### 2. 真实浏览器优先

对有登录态、动态页面和反爬机制的平台，不要默认 curl / requests 能可靠替代真实浏览器。

### 3. 分页完整性检查

逐字稿、长页面或长 API 响应必须检查：已经读取到哪里、总长度是多少、是否还需要继续分页。

最危险的不是“明显失败”，而是看起来像完整结果，实际只截取了前半段。

### 4. 不允许占位符冒充结果

如果逐字稿获取失败，应留空、标注失败原因并进入回退路径，不能用“完整内容已获取”之类占位文字代替真正内容。

**空缺是信息，假完成是数据污染。**

### 5. 受控标签

分类标签应优先从已有词表中选择，否则会出现 AI 教程、AI 入门、AI 学习、人工智能教程等近义标签不断分裂，最终破坏筛选。

### 6. 写入前后都要校验

至少检查主键 / 视频链接、重复记录、关键字段空值、文本是否异常短、是否有占位符、日期和字段类型、输出数量是否等于预期。

## 十一、安全与合规边界

### 本地权限

不要因为“方便”就授权整个硬盘。

### 企业数据

连接器和企业知识库涉及账号权限、数据分类、内部合规、日志与审计。是否适合某个组织，不能只凭“国产工具”或“和飞书打通”判断。

### 公开平台数据

“公开可见”不自动等于可以无限批量抓取、重新分发、商业使用或绕过平台访问控制。实际使用仍应遵守平台条款、著作权、个人信息与隐私规则和业务所在地适用法律。

### 自动发送与发布

任何对外发布、邮件发送、社交账号操作、删除、支付、邀请成员，都应提高人工确认等级。

---

## 十二、适合什么场景

豆包工作这类桌面 Agent 更适合：资料齐全、结果可检查的办公任务；长周期项目；文件批处理；调研与结构化输出；表格分析；重复流程自动化；团队协作底座已经在飞书的场景；需要本地文件与浏览器协同的任务。

不适合把它当作“自动正确”的全能员工、不设边界直接控制所有文件和账号的助手，或免验证的高风险决策系统。
