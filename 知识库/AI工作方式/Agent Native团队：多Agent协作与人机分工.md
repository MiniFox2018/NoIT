# Agent Native团队：多Agent协作与人机分工

## 核心问题

当一个人开始同时使用多个 Agent，问题很快会从：

> “AI 能不能完成这个任务？”

变成：

> “这么多 Agent 怎么分工、共享上下文、并行工作、交付和验收？”

Agent 能力提升以后，效率瓶颈不一定还在模型生成速度，而可能转移到：

- 人没有及时定义下一批任务；
- 多个 Agent 重复工作；
- 上下文在不同 Agent 之间丢失；
- 人需要逐个盯住所有执行过程；
- 结果完成后等待人工 review；
- 大量工作因为“等人决策”而停住。

因此，Agent Native 工作方式的重点不是“多开几个 AI”，而是建立一个**任务编排、上下文共享、执行、验证和人工介入机制**。

---

## 一、不要把 Agent 当聊天窗口，要把它当执行单元

单个 Agent 通常可以具备：

- 身份；
- 工作职责；
- 固定指令；
- Skills；
- 模型配置；
- 执行环境；
- MCP 或外部工具；
- 历史任务记录；
- 并发限制。

当这些配置可重复使用时，Agent 就不再只是一次性的聊天 Session，而可以成为长期复用的“执行角色”。

Multica 当前官方文档将 Agent 定义为工作区内可重复使用的一组身份、能力和执行配置。Agent 可以被分配 issue、被 @ 提及或直接对话，并通过绑定的 runtime 驱动实际 AI coding 工具完成工作。

需要区分三个对象：

| 对象 | 负责什么 |
| --- | --- |
| Agent | 谁来做，以及以什么规则做 |
| Runtime | 在哪台机器、通过什么 Agent 工具执行 |
| Run | 某一次具体执行过程和结果 |

这种分离很重要，因为：

- 同一个 Agent 可以执行很多次任务；
- 一个 runtime 可以承载多个 Agent；
- 换模型并不一定意味着换角色；
- 执行机器下线后，Agent 的身份和历史仍可以保留。

---

## 二、三个最常见的逻辑角色

腾讯研究院对 Multica 创始人的访谈中，总结出一个很实用的三角色模型：

### 1. Orchestrator：协调者

主要负责：

- 理解目标；
- 拆解任务；
- 识别依赖关系；
- 分配任务；
- 追踪状态；
- 汇总结果；
- 决定什么时候需要继续拆分。

### 2. Worker：执行者

主要负责：

- 接收清晰任务；
- 实际执行；
- 产生代码、文档、分析或其他交付物；
- 返回结果和阻塞点。

### 3. Validator：验证者

主要负责：

- 检查结果是否满足要求；
- 做测试；
- 找错误；
- 检查遗漏；
- 对照验收标准；
- 决定是否需要返工。

这三个角色是**逻辑职责**，不一定要求三个不同 Agent。

同一个通用 Agent 在不同任务中可以切换角色。

真正重要的是：

> 每一个任务都必须有人或 Agent 负责“拆”、有人负责“做”、有人负责“验”。

如果只强调 Worker，Agent 数量再多，也只是更快地产生未经验证的输出。

---

## 三、多Agent不等于层级越多越好

访谈中的团队提出“最多两层”的经验：

- 第一层：协调；
- 第二层：执行。

这是一个具体团队的实践经验，不应该当成所有 Agent 系统的绝对规则。

但背后的原则值得保留：

> Agent 架构的目标是减少协调成本，而不是模仿传统公司的组织图。

增加一层 Agent，就意味着增加：

- 一次信息转译；
- 一次上下文压缩；
- 一次状态同步；
- 一个潜在误解点；
- 一段额外延迟。

只有当新增层级确实能解决：

- 任务规模；
- 权限边界；
- 专业化；
- 风险隔离；
- 上下文容量；

等实际问题时，才值得增加。

---

## 四、尽量减少“人作为中间转发器”

传统协作经常出现：

```text
负责人
→ 告诉项目经理
→ 项目经理转给执行者
→ 执行者再告诉 AI
```

每一次转述都会发生：

- 信息压缩；
- 语义偏移；
- 上下文丢失；
- 等待。

如果中间角色只是机械转述，而没有真正增加判断价值，可以考虑缩短链路。

一个更 Agent Native 的思路是：

```text
目标负责人
→ 直接定义任务给 Agent
→ Agent执行
→ 负责人或验证Agent验收
```

这也是为什么“一人端到端负责一个结果”开始变得更有价值：

- 同一个人拥有完整上下文；
- Agent 弥补执行能力；
- 减少跨人 handoff；
- 最终责任边界更清楚。

但这并不意味着所有团队都应该取消专业分工。

在高风险、复杂或跨领域工作中，专业 review 仍然重要。

---

## 五、人应该留在哪里

“什么都交给 Agent”不是成熟的人机分工。

更稳妥的判断维度包括：

### 1. 方向

应该做什么、为什么做，通常仍需要人负责。

### 2. 目标和验收标准

如果没有定义“什么算完成”，Agent 再强也容易优化错误目标。

### 3. 高风险决策

法律、财务、安全、品牌、重大产品方向等，不应只因为 Agent 输出稳定就取消必要的人工责任。

### 4. 人际关系

用户访谈、复杂谈判、建立信任、敏感沟通等场景，人本身通常是交互的一部分。

### 5. 品味和特殊判断

AI 能生成大量平均质量不错的结果，但对“为什么这个方向值得做”“什么是我们独特的判断”等问题，人仍应主动形成自己的观点。

### 6. 最终责任

Agent 可以执行任务，但不能替组织承担现实世界的责任。

---

## 六、人可能成为新的吞吐瓶颈

当 Agent 可以并行执行大量任务时，一个新的问题会出现：

```text
Agent 生成速度
    >
人的阅读、决策、review 速度
```

这时任务会大量堆积在：

- 等人确认；
- 等人 review；
- 等人做优先级排序；
- 等人回答问题；
- 等人继续拆任务。

访谈中的“人是最慢的节点”描述的是这个特定 Agent-heavy 团队观察到的现象，不应当作所有组织的普遍定律。

但它提醒了一个真实的系统设计问题：

> 提升 Agent 并发以后，还必须重新设计人工介入点。

否则增加更多 Agent 只会制造更大的 review 队列。

---

## 七、不要用“Agent闲置率”当唯一效率指标

该团队提出通过 Agent idle rate 观察 AI Native 程度。

这个指标可以帮助发现：

- 是否花钱部署了大量 Agent 却很少真正使用；
- 是否因为人没有持续提供任务而造成执行资源闲置；
- 是否任务拆解粒度太大，无法形成持续并行。

但它不能单独代表组织效率。

如果盲目追求“Agent 24 小时都在跑”，可能产生：

- 没必要的任务；
- 低价值分析；
- 更多垃圾输出；
- 更大的 review 压力；
- 更高 token 和基础设施成本。

更完整的指标应该同时考虑：

- 有价值任务完成量；
- 返工率；
- 验收通过率；
- 人工 review 时间；
- 单位结果成本；
- 任务等待时间；
- Agent 间重复劳动；
- 最终用户价值。

Agent 不闲着不是目标。

**高价值工作流顺畅才是目标。**

---

## 八、并行工作的前提：任务必须可分解

多 Agent 最大的价值之一是并行。

但不是所有任务都适合并行。

适合并行的任务通常具有：

- 输入边界清楚；
- 输出格式明确；
- 相互依赖较少；
- 可以独立验收；
- 失败后容易重试。

例如：

- 多份资料并行研究；
- 不同模块的独立实现；
- 不同假设的并行验证；
- 测试、文档和数据分析并行；
- 多方案探索。

不适合强行并行的任务：

- 高度共享同一个上下文；
- 下一步完全依赖上一步；
- 核心决策还没确定；
- 多 Agent 很容易同时修改同一个关键对象。

Agent Native 的重点不是“并发最大化”，而是：

> 把可以并行的部分并行，把必须串行的依赖保留下来。

---

## 九、共享上下文比“多模型”更重要

多个 Agent 各自聪明，但如果它们：

- 看不到同一个目标；
- 不知道其他 Agent 做过什么；
- 使用不同版本的规则；
- 无法看到统一任务状态；
- 没有共同知识库；

那么系统很快会出现重复和冲突。

因此，多 Agent 系统通常需要某种共享层：

- workspace；
- issue / task；
- shared docs；
- project rules；
- knowledge base；
- artifact store；
- status history。

这也是 [[LLM维护型个人知识库：从RAG到持续演化的Wiki]] 和 Agent 编排会自然连接的原因。

一个负责**持续保存上下文和知识**，另一个负责**让多个执行单元围绕这些上下文工作**。

---

## 十、平台和模型中立更适合长期系统

Multica 当前的一个核心方向是让多个 Agent 工具工作在同一工作空间中，而不是把组织绑定在单一模型或单一 Agent 上。

长期来看，这种平台中立设计有几个优势：

- 可以按任务选择不同模型；
- 模型升级时不用重建整个流程；
- 避免知识和工作流锁死在单一聊天产品；
- 同一任务体系可以跨本地机器、服务器和不同 runtime；
- 规则与历史可以独立于模型存在。

这和 NoIT 把长期规则写入 GitHub 仓库，而不是依赖某个 AI 平台的内部记忆，是同一种设计思想。

---

## 十一、信任应该通过验证逐步建立

一个常见误区是把 Agent 使用分成两种：

- 完全不信；
- 完全自动。

实际上更合理的是逐步建立信任：

### 第一级：所有结果人工检查

适合新 Agent、新任务或高风险工作。

### 第二级：Agent 先自检，人抽查

适合已经比较稳定的流程。

### 第三级：低风险任务自动通过，高风险任务人工 review

通过规则和风险分层决定介入程度。

### 第四级：只有异常才请求人工介入

成熟流程可以只把：

- 失败；
- 不确定；
- 冲突；
- 权限不足；
- 高风险动作；

推入人的 inbox。

这比“所有任务最后都让人看一遍”更容易扩展。

---

## 十二、保留人的独立思考能力

采访中一个非常重要但容易被忽略的问题是：AI 使用越来越多以后，人可能逐渐减少独立思考的时间。

这不是已经被证明必然发生的结果，但它是值得主动防范的工作方式风险。

可以设计一些“AI 前”的步骤：

- 重大决策先自己写第一版判断；
- 先列出自己的假设；
- 先写出支持和反对理由；
- 再让 AI 补充、反驳、找遗漏；
- 定期写 journal；
- 保留没有 AI 参与的阅读和思考时间。

这样可以避免整个工作流程变成：

```text
遇到问题
→ 立刻问 AI
→ 接受一个看起来合理的答案
```

更好的方式是：

```text
形成自己的初始判断
→ 用 AI 扩展和挑战
→ 综合后做最终判断
```

这与 [[AI辅助的系统化学习与输出工作流]] 中“AI 负责降低机械成本，人负责真正理解和判断”的原则一致。

---

## 十三、一个可复用的 Agent Native 工作流

```text
确定目标
    ↓
定义完成标准
    ↓
拆解任务与依赖
    ↓
判断哪些可以并行
    ↓
分配给 Worker / Agent
    ↓
共享统一上下文和规则
    ↓
Agent 执行并回报阻塞
    ↓
自动验证 / Validator 检查
    ↓
仅把必要问题升级给人
    ↓
人工做关键判断和最终验收
    ↓
把成功流程沉淀为 Skill / 规则 / 知识
```

真正可持续的 Agent Native 系统最终会不断把：

- 成功做法；
- 检查规则；
- 常见错误；
- 任务模板；
- 领域知识；

从一次性执行经验变成下一次所有 Agent 都能复用的长期资产。

---

## 十四、对个人使用者同样适用

这套方法不只适用于公司。

个人同时使用 ChatGPT、Codex、Claude Code、Manus 或其他 Agent 时，也会遇到相同问题：

- 任务重复交代；
- 平台之间上下文不一致；
- 规则漂移；
- 结果散落在聊天中；
- 不知道哪个 Agent 做过什么。

个人版的最小实现可以很简单：

1. 用 GitHub 仓库保存项目事实；
2. 用 `AGENTS.md` / 规则文档保存长期工作规则；
3. 每个任务先读仓库最新状态；
4. 不同 Agent 都对同一套文件工作；
5. 产出回写仓库；
6. 人负责最终方向和重要 review。

NoIT 当前本身就是这种跨 Agent 共享知识和规则层的一种实现。


## 十五、Tiny Team：人数少不是目标，高杠杆才是目标

Latent Space 对一批高收入小团队的观察，提供了一个很有价值的补充：AI Native 组织不只是“把 Agent 接进现有公司”，还可以从一开始就把公司设计成低协调成本、高自动化、高个人杠杆的系统。

这些团队的共同做法不能直接视为普遍定律，但可以抽象出几条长期原则。

### 1. 招聘宁缺毋滥

小团队中，每一个人都会显著改变团队平均能力与沟通成本，因此更适合：

- 招真正愿意投入这个问题的人；
- 用付费试做、短期合作或真实任务观察能力；
- 优先选择能跨边界解决问题的高级通才；
- 用更少的人换取更清晰的责任与更高的人均产出。

“人数越少越好”不是原则。真正要减少的是**不创造价值的协调层和 handoff**。

### 2. 保护深度工作时间

Tiny Team 常见做法包括少会议、异步信息、明确 owner、集中处理异常。

其底层逻辑与 Agent Native 一致：

> 不要让所有人持续同步所有事情，而要让信息只在需要决策时升级。

### 3. 把一次成功做法变成可复用资产

团队规模小，意味着重复劳动尤其昂贵。

因此应持续把：

- SOP；
- Prompt；
- Agent workflow；
- 模板；
- 检查清单；
- 支持回复；
- 分析流程；

固化为下一次可以直接调用的资产。

AI 的真正杠杆不是“某次回答快了几分钟”，而是让过去的工作持续降低未来工作的边际成本。

### 4. 对用户保持高带宽

自动化不能等于远离用户。

小团队反而更需要创始人和核心成员持续接触：

- 销售；
- 客服；
- 产品反馈；
- 流失原因；
- 真实使用场景。

这样才能防止自动化系统高效执行一个错误方向。

## 十六、AI 原生创业公司的四阶段操作系统

Anthropic 2026 年的 Founder’s Playbook 把创业过程拆成 Idea、MVP、Launch、Scale 四个阶段。值得吸收的不是某个 Claude 产品用法，而是**不同阶段应该交给 AI 的工作不同**。

### Idea：扩展研究，但不外包判断

AI 适合：

- 整理竞争格局；
- 汇总公开用户反馈；
- 生成访谈问题；
- 对假设做反例搜索；
- 把大量材料压缩成可比较结构。

人仍应负责：选择问题、识别真正痛点、形成自己的判断。

### MVP：加速实现，但明确边界

AI 生成代码或流程以后，仍需要提前定义：

- 核心范围；
- 架构边界；
- 数据与安全要求；
- 验收条件；
- 哪些技术债可以接受，哪些不能。

否则“写得快”可能变成更快地积累不可维护的系统。

### Launch：把创始人注意力从重复执行中释放出来

进入发布阶段后，可逐步把高频、规则化工作 Agent 化，例如：

- 线索研究；
- 内容加工；
- 客服初筛；
- 数据汇总；
- QA；
- 运营检查；
- 例行报告。

重点不是自动化数量，而是让创始人把时间重新投入用户、产品方向和关键关系。

### Scale：建立指标、权限和异常升级机制

规模增长后，Agent 系统必须从“能做事”升级到“可治理”：

- 观察业务指标；
- 记录执行痕迹；
- 明确权限；
- 设风险阈值；
- 对异常自动升级；
- 对关键决策保留人工责任。

四阶段可以概括成：

~~~text
Idea：扩大认知
MVP：扩大执行
Launch：扩大吞吐
Scale：扩大系统，同时控制风险
~~~

这比“从第一天就全自动化”更符合组织演化规律。



## 十七、把“Who Not How”扩展为“谁 / 什么执行单元最适合”

《10倍成长思维》中“成事在人不在于方法”的可用部分，与 Agent Native 的核心高度一致：

> 负责人不应默认亲自学会并执行所有步骤，而应先判断谁或什么系统最适合承担这项工作。

在 AI 工作流里，“Who”不再只代表另一个人，也可能是：

- 专业同事；
- 外包；
- AI Agent；
- 自动化脚本；
- SaaS；
- 固化后的 Skill / SOP。

一个实用的分配顺序是：

1. **方向、价值判断、高风险责任**是否必须由人保留？
2. 如果任务高度重复且规则稳定，优先考虑**自动化**；
3. 如果任务需要大量语言理解、资料处理或低风险判断，考虑**Agent**；
4. 如果任务依赖信任、谈判、复杂关系或现实责任，保留**人工 Owner**；
5. 任何重复成功的 Agent 流程，都应继续沉淀为规则、Skill、模板或自动化资产。

无论交给人还是 Agent，委托包至少要包含：

~~~text
目标结果
+ 上下文
+ 边界
+ 质量标准
+ 验证方法
+ 异常升级条件
~~~

这与本文件前文“人不应成为所有任务的中间转发器”“成熟流程只把异常升级给人”是一致的。
