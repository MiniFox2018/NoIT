# AI产品工程：评测、上下文与系统优化

## 核心原则

AI 产品工程是把模型变成用户真正能使用的产品。模型效果不好时，不能直接推导出“需要更强模型或微调”。从真实失败数据出发，用评测看清问题，再优先修复检索与上下文、执行系统和资源配置；后训练放在这些杠杆用尽后评估。Hamel Husain 于 2026 年 8 月整理的 13 场课程围绕 Evals（4 场）、Context（5 场）、Systems（4 场）展开。

整体工作流：收集生产 trace → 人工分析错误 → 设计 eval → 修复简单缺陷 → 优化检索与上下文 → 优化执行和部署 → 必要时才做后训练 → 持续回归评测。

## 第一部分：Evals（1—4）

### 1. Data Agent Benchmark：真实任务不能太干净

DAB 以跨至少两个数据库、不一致的关联键、自由文本中的关键值、含糊 schema 等还原生产数据问题。重要失败模式不是简单“找错数据”，而是 Agent 先拟订计划，即使后续证据冲突仍执意执行。需要评估模型能否基于新证据修正计划，并区分通用 benchmark 与本产品真实用户问题的测试。

### 2. Model Cascade：小模型信心足时不必调用大模型

BARGAIN 以小模型置信度决定是否升级。实际步骤：抽取代表性样本（来源示例约 500 条）→ 用大模型构建比较标签 → 测量小模型置信度 → 寻找满足质量目标的最便宜阈值 → 在独立样本复核 → 监测数据漂移。

**关键边界**：这里的“质量”首先是与大模型标签一致，不等于人工判断的绝对正确。来源介绍的“最多降低 86% 成本”和进一步 48.5% 等数字只对应论文实验场景，不宜推广为用户的预计收益。

### 3. Error Analysis：先看失败，再写 rubric

先抽样真实轨迹由人归纳失败模式，再由 LLM 辅助回溯历史案例、发现相似轨迹并用主动学习挑样本。分类 taxonomy 由可观察的错误演化，不能先要求模型凭空编好几十类错误标准。每个分类要能对应可重现的任务、触发条件、影响和修复建议。

### 4. Putting Evals into Production：先定义什么是好

Nova Escola 案例的顺序是：真实错误分析 → 可操作的评分标准 → 专家人工标注 → 校准 LLM judge → 小流量持续回归监测（来源案例为每日对约 2% 生产流量测试）。两名标注员高度不一致通常提醒团队的评分标准本身不清楚。能通过很小 prompt 改动稳定修复的问题不必全部投入复杂自动评估器。

## 第二部分：Context（5—9）

### 5. 多向量检索：质量和工程成本一起看

单文档一个向量容易压缩掉细粒度信息。ColBERT 类型 late interaction 采用逐 token 匹配、MaxSim 汇总相似度，质量可能提升但计算及索引较昂贵。SMVE 通过稀疏表示、倒排索引筛候选、最终精确匹配降低成本。是否采用必须在自己的长文、复杂术语和任务上对照单向量/BM25 测试；来源中的十亿文档 p99 延迟数字属于特定实验环境。

### 6. 搜索 Agent 的三种改进路径

- ORBIT：自动构造并验证多跳检索题，避免测试集全是单轮关键词即可命中的简单问题。
- Hawkeye：可视化搜索轨迹，找无效搜索、反复迂回和失败恢复问题。
- BrowseComp-Plus：同一模型得到错误资料和正确资料时成绩可差异巨大；来源提供 14.6% 对 93.5% 的对比，但只能描述其特定检索环境。

评价搜索工具时要同时看证据覆盖、回答忠实度、检索轮数、延迟和调用费用。

### 7. Embedding：不要只照着排行榜选

真实选型维度包括自家领域检索质量、多语言表现、上下文长度、量化损失、推理成本及索引大小。可实验 INT8、FP16/BF16、二值化和 Matryoshka 截断维度。若领域匹配质量不佳，微调 embedding 往往比直接后训练 LLM 更便宜；必须用自有验证集确认收益。

### 8. OCR：先保证进入系统的信息是真的

先明确是只需文本还是要段落、表格与完整文档结构；再比较托管 API、自托管 OCR、视觉语言模型。使用 50—100 页代表样本包含双栏、扫描、表格、TeX 排版、空白页和复杂脚注。

典型失败：PDF 抽取缺空格、阅读顺序跨栏、扫描文本瞎填、空白页面幻觉出内容。每种候选都必须检查原始抽取与对应页面；厂商价格、许可和部署条件属于动态信息，不能把 2026 年 8 月课程数值当永久现价。

### 9. Subtext：以旁注保留作者没有明说的约束

重要备忘录中的“为什么这样决策”常藏于字里行间。Subtext 的做法是保留原句不动，在旁注中记录作者澄清、相关背景与待解问题，使改写 Agent 不会悄悄丢失决策条件。可迁移到方案、合同、评测记录和知识管理，但旁注不能替代来源证据。

## 第三部分：Systems（10—13）

### 10. 推理延迟：分清 prefill 与 decode

Prefill 主要处理输入上下文；decode 逐 token 生成输出，长输出常成为性能瓶颈。优化时先按真实请求区分长入短出、短入长出和短入短出，再测 TTFT、输出吞吐、总延迟。decode 主导时先考虑删减不必要输出；prefill 主导时改善上下文长度、缓存或批处理。模型量化、vLLM、llama.cpp、投机解码、硬件更换都是后续对照实验，而非先验万能解决方案。

### 11. 开源模型经济学：完整算账

权重显存粗估约为参数量（十亿）×位宽/8 GB；例如 27B 以 4-bit 表示仅权重约 13.5 GB，仍需为 KV cache、激活和运行时留空间。总成本还包括并发、吞吐、故障恢复、部署人员、GPU 租赁、多机网络开销与数据保密。来源中的某些具体模型排名和租卡价格具有明显时效，使用时应重新验证。

### 12. Agent 沙箱：隔离文件、权限与工具失败

多个 Agent 并行、长任务修改依赖或执行不审阅代码时，要有独立环境、受限凭据、网络策略和审计。预烘焙镜像降低启动成本；将工具进程和 Agent 主轨迹隔离，避免加载大 CSV 造成工具崩溃时连带杀死整个任务。CI 是测试与交付机制，不能直接替代长期可修改的 Agent 沙箱。

### 13. 后训练：评测工具本身可能是瓶颈

先读 trace，检查评测规则、时间预算、max tokens、轮数限制、CPU/内存、harness 和必要 Skills 是否正常，再考虑微调或 RL。来源中 Terminal-Bench 2 增加超时上限后从 46.3% 到 60.97% 的数字，是环境调整导致的案例，不等于任何模型通用提升幅度。

需要同时满足：结果有可靠自动验证方法；当前表现有改进空间而非零分或满分。否则 RL 可能优化错误奖励。

## 可执行验收矩阵

| 环节 | 必留资产 | 验收条件 |
|---|---|---|
| 用户需求 | 真实场景与错误代价 | 正反样本覆盖 |
| 错误分析 | trace 与人工分类 | 可复现、可追踪 |
| Eval | rubric、人工基准和 judge | 标注一致性及误判检验 |
| 检索 | 召回、证据覆盖、错误查询 | 真实语料、困难样本 |
| 执行 | 时延、算力、隔离、回退 | 不因环境配置产生假失败 |
| 成本 | 成本与质量曲线 | 不只比较单次价格 |
| 上线 | 生产抽查、回归报警 | 能追踪与修复新错误 |
