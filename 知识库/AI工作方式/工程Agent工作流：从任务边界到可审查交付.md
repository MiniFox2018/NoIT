# 工程 Agent 工作流：从任务边界到可审查交付

这份文档整理工程型 Agent 在真实项目中的长期工作方法。它吸收了《ChatGPT 橙皮书》中关于 Codex、Git/GitHub、任务拆解、测试、Review、AGENTS.md、Skill 和云端任务的有效部分，并结合 2026-10-03 可访问的 OpenAI 官方资料校正了已经变化的产品细节。

核心目标不是“让 AI 多写代码”，而是把一个明确的软件工程任务推进到**范围可控、过程可验证、改动可审查、失败可回滚、结果可交付**的状态。

## 一、先改变对工程 Agent 的理解

传统代码助手主要回答“这段代码怎么写”。工程 Agent 的工作对象是整个任务链：

1. 读取仓库和项目规则；
2. 理解目标、现状和约束；
3. 找到相关文件和执行入口；
4. 形成计划；
5. 修改文件；
6. 运行命令与测试；
7. 检查 diff；
8. 处理失败；
9. 整理提交、PR 与未验证项。

因此，衡量 Agent 的标准不应是“生成代码看起来像不像”，而应是：

- 是否修改了正确的范围；
- 是否保留原有约束和业务规则；
- 是否真实执行了验证；
- 是否能解释改动与风险；
- 是否留下可被人继续 Review 和维护的结果。

这与 [[复杂任务提示词与AI写作：任务设计、材料、工具、验收与返工]] 的通用任务设计原则一致，但工程任务额外要求版本控制、可运行验证和代码审查。

## 二、什么任务适合交给工程 Agent

适合委托的任务通常具有以下属性：

| 属性 | 判断问题 |
| --- | --- |
| 目标明确 | 最终到底要修复、增加、解释或交付什么？ |
| 范围可控 | 能否限定到仓库、模块、页面、接口或一组文件？ |
| 上下文可读 | Agent 能否取得代码、规则、日志和必要资料？ |
| 结果可验证 | 是否有测试、构建、lint、typecheck、浏览器检查或人工验收？ |
| 失败可回滚 | 是否有 Git 基线、分支、worktree 或备份？ |
| 风险可接受 | 即使失败，是否不会直接破坏生产环境或真实数据？ |

典型任务包括：读懂陌生项目、定位可复现 bug、增加边界清楚的小功能、补测试、重构局部重复逻辑、整理 README、检查构建失败、代码 Review、准备 commit 与 PR。

以下任务不应默认交给 Agent 独立执行：生产数据库操作、真实用户数据修改、支付与权限核心逻辑、密钥管理、安全边界修改、大规模架构迁移、没有备份的关键项目，以及人本身也无法判断结果正确与否的任务。

原则是：

> **自动化程度不能超过验证能力。**

越难验证、越难回滚、影响越大的任务，越需要缩小权限、增加人工审批和独立验证。

## 三、开始工作前先建立“现场”

Agent 进入项目后，不应立刻写代码。先建立一个可审查的工作现场。

### 1. 读取项目规则

优先读取：

- 根目录和相关子目录的 AGENTS.md；
- README、CONTRIBUTING、开发文档；
- package.json、pyproject.toml、Cargo.toml 等项目元数据；
- 测试、构建、lint、typecheck 命令；
- 与本次任务直接相关的文件。

AGENTS.md 的作用是给 Agent 提供**仓库级硬规则**，例如测试命令、目录约束、禁止事项和交付要求。它不适合塞入某一次任务的临时要求。

### 2. 检查 Git 基线

开始修改前至少确认：

- 当前分支；
- git status；
- 是否存在未提交改动；
- 当前任务是否应新建分支或 worktree；
- 是否有一个可以回滚的干净基线。

Agent 做得越多，Git 越重要。Git 不只是“上传代码”的工具，而是工程 Agent 的控制面：它提供变更边界、diff、历史、隔离、回滚和审查依据。

### 3. 先识别已有问题

运行验证时要区分：

- 本次修改之前就存在的问题；
- 本次修改新引入的问题。

否则 Agent 很容易把旧错误误认为自己的回归问题，继续扩大修改范围。

## 四、标准六步法

## 第一步：需求拆解

开始前把需求改写成可以执行和验收的任务契约，至少明确：

- 背景：为什么要做；
- 目标：希望最终发生什么变化；
- 范围：哪些模块或文件可能相关；
- 禁区：哪些功能、接口、目录、依赖不能动；
- 完成标准：怎样算真正完成；
- 验证方式：要运行哪些测试或人工检查；
- 风险：哪些位置出错代价较高。

一个可复用的任务契约：

~~~text
任务：
<要完成的具体结果>

背景：
<为什么要做，当前问题是什么>

范围：
- 允许修改：
- 优先检查：

限制：
- 不修改无关文件
- 不删除已有功能
- 不引入不必要依赖
- 发现需要超出范围时先说明

验证：
- 需要运行的测试 / 构建 / lint / typecheck
- 需要人工检查的页面或业务流程

交付：
- 列出修改文件
- 说明每项改动
- 报告验证结果
- 标明未验证项和风险
~~~

任务说明越接近“可验收合同”，越不需要靠长篇角色设定约束模型。

## 第二步：先形成计划

复杂任务先规划，不等于写一篇很长的计划文档，而是让 Agent 明确：

1. 先检查哪些文件；
2. 需要复现什么现象；
3. 准备怎样修改；
4. 会运行哪些命令；
5. 哪些环节需要人工确认；
6. 哪些结果决定下一步。

计划的价值主要有三点：

- 在写代码前暴露理解偏差；
- 提前看到可能越界的文件与命令；
- 给后续 Review 提供“计划内 / 计划外”的比较基准。

简单且边界明确的任务可以缩短计划；跨模块、架构、依赖升级或高风险任务则应保留更清晰的计划门槛。

## 第三步：小步实现

工程 Agent 最稳定的方式不是“一次做完整个项目”，而是把大任务拆成连续的小变更。

实践原则：

- 一次只推进一个明确功能点；
- 优先最小可行改动；
- 不顺手重构无关代码；
- 不因为“更优雅”就替换已有架构；
- 新增依赖必须有必要性；
- 大面积删除必须解释；
- 发现业务规则不确定时停止猜测；
- 发现必须超出计划范围时先重新规划。

“最小 diff”不是追求代码行数最少，而是让改动与需求之间保持可解释的一一对应关系。

## 第四步：验证

不能把“Agent 说测试通过了”当作验证。应查看真实执行结果。

常见验证层包括：

| 验证层 | 目的 |
| --- | --- |
| 单元测试 | 检查局部逻辑 |
| 集成 / 端到端测试 | 检查模块之间的真实流程 |
| typecheck | 发现类型层面的破坏 |
| lint / formatter | 检查规则和基础质量 |
| build | 检查项目是否能完成正式构建 |
| 浏览器 / UI 检查 | 检查视觉、交互和运行时错误 |
| 手动业务验收 | 检查“代码能跑但业务逻辑错”的情况 |
| 回归检查 | 确认旧功能没有被破坏 |

如果验证失败，不要无限“试一试”。先判断失败属于：

- 代码错误；
- 环境或依赖问题；
- 权限问题；
- 测试本身的问题；
- 旧有故障；
- Agent 对需求的误解。

## 第五步：Review

Review 的重点不是重新浏览所有代码，而是围绕风险和变化检查。

优先检查：

1. **范围**：是否只改了与任务相关的文件；
2. **删除**：是否误删 fallback、兼容逻辑、配置或仍被引用的代码；
3. **边界条件**：空数据、接口失败、重复提交、未登录、权限不足等；
4. **安全**：密钥、token、输入校验、鉴权、上传、数据库和权限边界；
5. **业务逻辑**：结果是否符合真实规则，而不是只看“能运行”；
6. **依赖和配置**：是否引入无关包、改变环境或部署方式；
7. **验证证据**：哪些检查真正运行过，哪些只是推断。

推荐两层 Review：

- Agent 自审：根据计划、diff、测试结果检查明显问题；
- 人工审查：重点判断业务语义、风险、品味和责任边界。

高风险修改可以引入独立 Reviewer 或第二个模型，但“多一个模型”只是增加发现问题的机会，不能替代人工责任。

## 第六步：提交与复盘

任务完成后还要形成可维护的交付记录。

Commit / PR 至少说明：

- 改了什么；
- 为什么改；
- 影响哪些文件和模块；
- 做了哪些验证；
- 有什么风险或未验证项；
- Reviewer 应重点看哪里。

如果本次任务暴露出长期可复用的信息，再决定它应进入哪里：

- 只对当前任务有效 → 保留在当前 thread / prompt；
- 仓库长期硬规则 → AGENTS.md；
- 重复出现的完整工作流 → Skill；
- 实时外部数据 / 受控动作 → MCP 或连接应用；
- 需要定时或条件触发 → Automation；
- 项目使用方式变化 → README、docs、.env.example、CHANGELOG 等项目文档。

不要把每次成功的提示词都直接塞进 AGENTS.md。复盘的目标是降低下一次返工，而不是无限积累指令。

## 五、Git、分支与 worktree：给 Agent 建立隔离层

### 1. Git 是默认安全网

最基本流程：

~~~text
修改前：确认 git status 和当前分支
修改中：持续查看 diff
修改后：运行验证
确认后：commit
需要协作：创建 PR
~~~

不要把 git reset --hard、git clean -fd 等破坏性命令当成常规回滚方式。存在未提交工作时，先确认会丢失什么。

### 2. 分支用于隔离目标

每个明显独立的功能或修复应有清楚的分支边界。这样 Review、回滚和合并都更容易。

### 3. worktree 适合并行 Agent

多个 Agent 同时处理同一仓库时，worktree 可以让每个任务拥有独立工作目录和分支，避免互相覆盖本地状态。

前提是任务本身可以独立拆分。不能因为“可以开多个 Agent”就强行并行高度耦合的工作。

### 4. 云端任务仍以 Git 为交接面

Codex Cloud 等云端执行方式可以在 OpenAI 管理的环境中处理仓库任务。本地继续开发前，要确认云端修改是否已经进入远端分支或 PR，并先同步最新状态，避免基于旧提交继续工作。

## 六、权限与命令安全

工程 Agent 能运行命令，因此权限设计属于工作流的一部分。

长期原则：

- 默认最小权限；
- 项目内读写与项目外访问分开；
- 网络访问按任务需要开启；
- 高风险命令要求人工确认；
- 密钥只放在专门的 secret / 环境变量机制中，不进入聊天、代码、README 或 Git；
- 生产系统、真实用户数据和高权限账号不要作为练习环境。

截至 2026-10-03，OpenAI Codex 当前配置文档仍提供 workspace-write 沙盒与 on-request 审批策略，可作为“允许在工作区内执行、敏感动作再确认”的实用基线。不同版本和工作区的具体选项仍应以当前文档和界面为准。

遇到看不懂的命令时，先要求 Agent 说明：

- 它要改变什么；
- 会影响哪些文件或系统状态；
- 是否可逆；
- 有没有更低权限的替代方案。

## 七、失败处理：停止“无限试错”

工程 Agent 失败并不罕见，真正危险的是连续失败后仍不断扩大修改。

建议在以下情况下主动停下：

- 同一个问题连续尝试数次仍失败；
- 每次修复都会引出新的无关错误；
- diff 快速膨胀；
- Agent 开始修改计划外文件；
- 无法解释根因；
- 需要更高权限才能继续。

暂停后要求形成一份失败摘要：

~~~text
请停止继续修改。

总结：
1. 原始问题是什么；
2. 已经检查了哪些证据；
3. 尝试过哪些方案；
4. 每个方案为什么失败；
5. 当前最可能的根因；
6. 下一步最小验证动作；
7. 哪些修改建议保留，哪些应撤回。
~~~

这样可以把“盲目重试”切换回“基于证据的调试”。

## 八、上下文应该分层，而不是都写进一个文件

《ChatGPT 橙皮书》中“把不同信息放到不同层”的思路值得长期保留，但具体产品入口会不断变化。更稳定的抽象是：

| 信息类型 | 更合适的载体 |
| --- | --- |
| 本次任务目标、临时限制 | 当前 prompt / thread |
| 仓库必须遵守的硬规则 | AGENTS.md |
| 重复执行的专项工作方法 | Skill |
| 外部系统的实时数据与受控动作 | MCP / connected app |
| 可安装、可分发的一组能力 | Plugin |
| 定期或条件触发的重复任务 | Automation |
| 项目说明和人类协作文档 | README / docs |

这套分层的核心价值是避免上下文污染：

- 临时要求不应长期化；
- 长期规则不应每次重复输入；
- 实时信息不应复制成静态“记忆”；
- 一个可复用工作流不应被压缩成一句 AGENTS.md 规则。

## 九、AGENTS.md 与 Skill 都要控制体积

2026 年 OpenAI 针对更强模型的最新实践明确提醒：随着模型能力提升，过去积累的大量脚手架、冗余 Skill 和 AGENTS.md 指令可能反而制造噪声。

因此长期维护时应定期做减法：

- AGENTS.md 只放稳定、项目级、必须遵守的规则；
- Skill 只承载真正重复且需要稳定步骤的工作；
- 能从代码、测试或项目结构直接推断的信息，不要全部重复写成规则；
- description 用于清楚描述触发条件，不要塞完整教程；
- 旧规则若已无必要，应删除而不是永久叠加；
- 新模型上线后重新验证原来的“最佳实践”，不要把旧补丁视为永久真理。

这与 NoIT 本身的“少即是多”原则一致：**规则越重要越应清楚，越不重要越不该占据长期上下文。**

## 十、一个稳定的工程 Agent 任务模板

~~~text
请先读取当前项目规则、相关文件和 Git 状态，再处理任务。

目标：
<最终需要交付的工程结果>

范围：
<允许修改的目录 / 模块 / 文件>

不要做：
- 不修改无关模块
- 不删除已有功能
- 不新增无必要依赖
- 不执行生产环境或真实数据操作
- 需要扩大范围时先说明原因

执行：
1. 先确认现状和可能根因
2. 给出简洁计划
3. 以最小改动实现
4. 运行项目已有验证
5. 查看并自审 diff

交付：
- 修改文件与原因
- 实际运行的测试 / 构建及结果
- 未验证项
- 风险与需要人工确认的地方
- 是否建议提交 / 创建 PR
~~~

这个模板的价值不在于固定措辞，而在于始终覆盖目标、范围、执行、验证和交付五个核心层。

## 十一、完成标准

一个工程 Agent 任务不应因为“生成了代码”就结束。至少检查：

- 目标是否真正实现；
- 修改是否保持在合理范围；
- 是否查看了实际 diff；
- 是否运行了可以运行的验证；
- 测试结果是否区分旧问题和新问题；
- 是否存在未解释的大段删除或新增依赖；
- 是否泄露秘密或扩大权限；
- 高风险业务逻辑是否经过人工 Review；
- 是否留下可回滚的 Git 状态；
- 文档与配置是否需要同步；
- 是否明确列出未验证项。

如果这些问题无法回答，任务仍然处于“生成阶段”，还没有进入“可靠交付阶段”。

## 十二、从真实故障中提炼 Agent 规则

[Grok Bot Field Notes](https://github.com/unicodef1wn/grokbot-field-notes) 是第三方作者根据公开的 Grok Bot 团队构建过程整理的工程规则、失败案例、角色和岗位 Playbook，**不是 xAI 官方编码规范，也不是这些工作流已在 NoIT 环境验证的证据**。其中值得复用的是以下可操作结构：

1. **先复现，再修复**：跑起应用，确认失败条件、触发动作与预期结果；开始前讲清任务边界和“不做什么”，验收指标必须可观察。
2. **验证比代码数量重要**：Bug 修复给出前后复现，界面改动给截图/录屏，性能改动给实际运行指标，无法证明就不视为完成。
3. **口头规范写入可读取规则**：用户和团队默认的审批门槛、发布习惯、禁止项、产品定位必须明示；否则 Agent 往往做出与团队预期冲突的“合理动作”。
4. **反模式要抽象，而不是记事故**：从失败事件中萃取普适原则，避免把人名、某一次路径和临时情况写进长期规则导致过拟合。
5. **职责和授权边界先于多 Agent 扩张**：每个角色定义其拥有/不拥有的范围、证据来源、交付接口与何时升级给人；先验证一个 Agent 的闭环，再考虑拆成多角色。
6. **高频例程需要成本约束**：自动检查、定期复盘和重复轮询都有时间/Token 成本，按变化速度、风险及收益决定周期。
7. **高风险动作保留人工确认**：特别是部署、迁移、权限、对外发送和资金操作。网页与用户提供资料均应当成数据源，而不能提升为新授权。

最小交付约束：`任务范围 → 可复现基线 → 验收证据 → 有界实现 → 实际验证 → 复盘可迁移原则`。来源库自述另有 40 个反模式、69 个角色定义及 9 套 Playbook；本轮只核查 README、AGENTS.md 和失败日志选段，**未逐份读完这些附录**。

## 十三、Vibe Coding 的双重检查：追根因与对抗式审查

一份面向非专业开发者的经验文章，把两个常用 Prompt 思路概括为：**先从基本事实重新推导根因，再站在可能破坏系统的角度主动找反例**。它们对应不同阶段，不可相互替代。

### 1. “第一性原理”不是魔法后缀，而是根因调查程序

单纯告诉模型“从第一性原理出发”，不能确保它绕过训练偏差或自动找到真因。把要求改成一组可检查动作更可靠：

1. 先还原**用户实际看到的错误**、预期行为与复现步骤；
2. 沿数据流追踪从输入、路由、处理、存储到最终输出的完整路径；
3. 分离直接触发因素、底层结构缺陷与监控缺口；
4. 为每一种原因寻找支持和反驳证据；
5. 比较局部补丁与系统性修复各自的收益、成本、迁移风险；
6. 修改后回归原故障，并确认同一类失效不会从其他入口再次发生。

文章给出的案例是一套资讯系统漏推了重要来源。最初的解释聚焦某个抓取环节被改坏；进一步检查后，作者称发现了更底层的流量路由问题。该叙述说明**“修复一个来源”与“查清整条链路为什么容许静默漏抓”不同**，但没有提供代码、监控和对照实验，因此不是经过独立验证的故障报告。

可复用的任务指令：

```text
不要立刻修补表面报错。先给出复现条件和调用链，
区分“触发因素、根因、检测失败”。
对每项根因列出可观察证据或缺失的日志。
比较最小修复与结构性修复，指出迁移风险。
在修改前先确定回归用例，修改后运行并报告实际结果。
```

### 2. 对抗式审查要落到输入、状态与资源边界

审查者假定系统会遇到异常而不是只遇到善意的正常输入。至少覆盖：

| 审查面 | 代表性失效 | 应有验证 |
| --- | --- | --- |
| 极端输入 | 数十 MB 的 HTML、异常编码、嵌套标签、空内容 | 大小限制、超时、逐步解析、拒绝路径 |
| 资源与重试 | 内存耗尽后自动重试，再次耗尽 | 有界重试、退避、隔离队列、死信处理 |
| 时间 | 发布日期位于未来、时区转换出错 | 时间合法性、异常隔离、排序逻辑 |
| 上游来源 | 来源静默停止更新、返回错误内容 | 最后成功时间、数据量变化、告警 |
| 级联故障 | 一个异常任务阻塞所有 worker | 并发上限、隔离、熔断、监控 |
| 缓存与状态 | 假阳性健康检查、过期缓存误导 | 实际端到端探测、状态一致性 |
| 权限与隐私 | 无需的数据被上传、错误暴露凭据 | 最小权限、日志脱敏、数据范围审查 |
| 发布与回滚 | 修改通过单测却破坏历史行为 | 集成测试、灰度、可回滚发布 |

文章中的两个典型场景可以独立推导：

- **OOM 重试风暴**：遇到过大输入，worker 消耗超过限制；如果重试条件不变，任务可能无限失败。需要区分“瞬时错误可重试”和“确定性超限不应重试”。
- **未来时间污染**：采集端若接受异常未来时间戳，文章可能长时间占据“最新”排序、污染推送与报表。需要在入库和排序前统一时区、保存原始时间、判定异常并留痕。

这些案例可作为**测试设计线索**，不能当作上述所有故障已在原项目中被第三方确认。

审查提示可写成：

```text
对已实现功能做反例驱动审查。先列系统不变量和受信任边界。
从异常输入、空值、重复调用、时区、超大任务、超时、重试、
权限、并发和回滚逐项建立可复现测试。
每个发现给出：触发条件、影响范围、严重度、证据、修复建议。
没有复现证据的标为“假设性风险”，不得写作“已发现漏洞”。
```

### 3. 不能用“多 Agent 已审查”代替有效验证

增加 Agent 数量可以带来不同视角，也会增加成本、重复发现和互相污染的可能。更重要的是为每个审查者明确不同检查范围，并统一归并、复现、修复、回归测试。

完成一次代码检查，至少留下：

- 哪个 commit / 环境 / 配置被检查；
- 哪些测试实际运行、结果如何；
- 每个风险属于“已复现 / 推断 / 未验证”哪一层；
- 修复改变了哪些文件或行为；
- 旧功能是否通过回归；
- 哪些高风险操作还需要人工审批。

原作者称自己约每 2—3 周做一次全局审查，这是个案中的工作节奏。NoIT 不将其固化为所有仓库的统一周期，复核频率应随变更速度、故障影响和安全风险动态调整。

与 [[第一性原理与工程优化：从真相到五步算法]] 的关联：第一性原理帮助质疑隐含前提；与本篇工程流程的关联：对抗式审查把反例落实成**有证据的测试与可回滚修改**。

## 十四、从既有系统提炼「功能交接包」再重构

对于历史债务重、模块耦合的系统，不宜仅用「请全面重构」让模型对旧代码直接改写。AIHOT 作者实践提出了另一种可能路径：

1. 对旧项目做功能审计：对用户可观察行为、输入输出、数据契约、权限、页面状态、异常、外部集成和运行指标建立清单。
2. 区分**必须兼容的产品契约**与**可丢弃的旧实现细节**；旧代码只是证据之一，用户体验、线上日志、接口调用方和历史测试也必须审查。
3. 输出交接包：功能矩阵、接口清单、数据迁移策略、不可回归需求、验收用例、已知缺陷和未确认项。
4. 用另一轮独立审查挑战功能遗漏、迁移风险及依赖链，不把「双模型都赞成」等同于独立的实测。
5. 按模块增量替换、并行核验或灰度迁移；先验证旧/新关键行为与数据一致，再切换流量，保留回滚计划。
6. 重构后复核性能、可维护性和权限，同时沉淀新架构地图供后续 Agent 缩小上下文读取范围。

当旧系统存在真实数据、外部兼容或监管义务时，完全脱离代码从零重写可能遗漏关键行为。**功能蒸馏是需求基线，不是可替代测试和数据迁移的万能方案。**

## 十五、Codex 的初次实践：范围、权限、审查、迭代

来自非工程用户的详细教程可提炼为这条跨界面适用的稳定执行链：

- 确定**工作入口**：云端任务适合可访问的仓库任务；桌面应用适合日常审阅与本地工作；CLI 适合可脚本化操作；IDE 适合贴近代码完成局部改动。界面、套餐与安装命令随版本变化，统一从官方入口核对。
- 指定**项目根目录**，先读取 README、AGENTS.md、测试和当前 Git 状态；明确非目标与禁止操作。
- 将第一条指令写成「我要什么 → 读哪些材料 → 哪些文件能动 → 交付什么 → 怎么测试 → 先汇报风险」。不要只说「帮我做个网站」。
- 让 Agent 先给变更计划与受影响文件，必要时人确认后再执行。不要默认给全盘读写、网络和命令执行权限。
- 查看 diff、命令历史、预览页和测试输出；运行关键功能场景，再接受变更。
- 修正时用可复现的 bug、期望行为与截图缩小范围；通过 Git 分支或提交保留回滚点。
- 不把作者「月入 10w+」视为 Codex 的普遍产出能力，也不把截图中的应用菜单、收费、安装途径当作目前不变的官方操作步骤。

### 可复用项目级 AGENTS.md 要点

只写项目是什么、目录入口、构建与测试命令、必须先问人的红线、代码或文档风格、隐私与密钥边界、交付前检查。长背景留在独立文档，避免在每次任务里加载同一份无关材料。
