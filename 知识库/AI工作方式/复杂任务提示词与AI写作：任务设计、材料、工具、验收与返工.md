# 复杂任务提示词与AI写作：任务设计、材料、工具、验收与返工

## 这套方法解决什么问题

提示词工程的重点不应只是：

> 怎样把一句话写得更“厉害”。

对于长文写作、研究、数据分析、文件修改、资料整理和 Agent 工具任务，更重要的问题已经变成：

- 最终到底要交付什么；
- AI 还缺哪些业务背景；
- 当前动作是什么；
- 应使用哪些材料；
- 哪些材料只是风格参考，哪些可以作为事实依据；
- 需要调用哪些工具；
- 哪些操作有权限边界；
- 执行顺序是什么；
- 什么情况下必须停下来问人；
- 最后怎样验证任务是否真正完成。

可以把这种工作方式理解为：

> **把 Prompt 从一句“生成要求”，升级成一份任务说明书。**

简单任务依然应该简单说清，不需要把每次对话都写成合同；只有当任务复杂度、风险、材料量或工具依赖提高时，才逐步展开完整结构。

## 一、所谓“AI味”，通常不是某一个词，而是内容系统出了问题

低质量 AI 文案经常被概括成“AI味”。

真正的问题通常不只在“赋能、闭环、抓手”这类高频套话，而是多个层次一起失控。

可以把常见问题拆成七类。

### 1. 内容正确，但没有执行信息

例如：

- 提升产品品质；
- 优化服务体验；
- 加强客户关系；
- 构建品牌价值。

这些话未必错误，但如果没有回答：

- 具体改什么；
- 当前问题在哪里；
- 谁负责；
- 预算是多少；
- 什么时候执行；
- 如何验证；

读者看完仍然不知道下一步做什么。

判断标准很简单：

> **删掉一段以后，如果读者没有损失任何新信息，这一段大概率只是正确废话。**

### 2. 高频套话替代了真实信息

常见表现包括：

- 宏大背景开场；
- 固定的“值得注意的是”；
- 过度使用行业热词；
- 结尾机械升华；
- 形容词很多，事实很少。

问题不是某个词永远不能用，而是同一批高概率表达被不断重复，导致文章失去作者自己的信息密度与语言辨识度。

### 3. 句式过度整齐

典型表现：

- 首先、其次、最后；
- 每段长度相近；
- 每段都是“观点 → 解释 → 总结”；
- 频繁使用同一套转折模板；
- 全文节奏没有变化。

文章结构工整并不等于错误。真正的问题是：

> 结构开始盖过内容，读者可以提前猜到下一句。

改善方法不是故意把句子打乱，而是让信息重要性、场景变化、逻辑推进、动作和证据自然决定段落长度与节奏。

### 4. 每个局部都通顺，但整篇没有主线

模型很容易把相邻句子接顺，却不一定自动守住全文唯一的核心问题。

因此可能出现：

~~~text
标题回答问题 A
↓
正文第一部分解释 A
↓
第二部分跳到 B
↓
第三部分开始罗列工具 C
↓
结尾升华到 D
~~~

解决办法是提前明确：

- 这篇内容只解决什么问题；
- 哪些内容即使“有用”也不属于当前主线；
- 每一节怎样服务最终结论。

### 5. 缺少现场事实，只剩通用常识

AI 并不知道你的真实业务流程、内部数据、历史决策、组织限制、客户反馈、个人经历、成本结构和现场细节。

如果这些信息没有进入任务上下文，模型就只能从通用知识中补齐。

因此，很多“看起来什么都懂、实际不能执行”的输出，本质上不是文笔问题，而是：

> **任务材料不足。**

### 6. 罗列所有选项，却没有形成条件化判断

一种常见输出是：

1. A 有这些优点；
2. B 有这些优点；
3. C 也有这些优点；
4. 最后请结合自身情况综合判断。

这种回答把决策成本原样退回给用户。

更有价值的写法应该变成：

~~~text
如果目标是 X，且满足条件 Y → 选 A
如果主要约束是 Z → 选 B
达到某个阈值后 → 再切换到 C
~~~

AI 不需要替人承担最终责任，但应该在已有事实足够时，把条件和取舍说明清楚。

### 7. 虚构数据、案例、来源与引用

这是最危险的问题。

当任务涉及行业数据、论文、DOI、法律法规、财报、白皮书、新闻、产品能力或实时价格时，不能因为答案“写得像真的”就视为可靠。

因此复杂写作任务必须提前规定：

- 哪些事实必须有来源；
- 哪些来源可以作为证据；
- 没有资料时写“未提供 / 待确认”；
- 不得为了文章完整度自行补造数字、案例和出处。

## 二、Prompt、上下文、材料、工具不是同一个东西

复杂 AI 任务里，最容易混淆的是：

> “我输入了什么”与“模型这一轮实际拿到了什么”。

可以把任务环境拆成几层理解。

### 1. 系统与运行规则

平台本身会规定：

- 哪些工具可用；
- 哪些操作受限；
- 哪些动作需要确认；
- 工具怎样返回结果；
- 安全与权限边界。

这些规则不是当前用户 Prompt 可以随意覆盖的。

具体优先级和实现方式由平台决定，因此不应把某一产品的内部层级写成所有 Agent 系统的普遍定律。

### 2. 项目规则与可复用流程

项目中可能存在：

- AGENTS.md；
- PROJECT_RULES.md；
- SKILL.md；
- 工作流说明；
- 模板；
- 项目配置。

它们负责表达：

> **这类任务平时应该怎样做。**

NoIT 自己就是这个模式：PROJECT_RULES.md 保存长期规则，AGENTS.md 作为 AI 工具入口，当前用户要求决定本次任务的具体目标。

### 3. 当前提示词

当前 Prompt 负责说明：

> **这一次到底要做什么。**

它通常可以包括：

- 角色或视角；
- 任务结果；
- 核心动作；
- 业务背景；
- 材料说明；
- 边界；
- 输出方式；
- 验收标准。

其中最重要的是明确动作。

“帮我看看”与“提取、比较、核对、计算、改写、生成、修改、验证”不是同一个清晰度等级。

### 4. 历史对话

历史对话提供已经确认的目标、用户偏好、前面做过的决定和当前项目状态。

但历史越长，越容易同时留下：

- 已作废数字；
- 旧方案；
- 过时约束；
- 被后续推翻的结论。

因此当关键条件变化时，最好显式重述最新状态。

一个长期原则是：

> **最新明确条件覆盖已经被更新的旧条件。**

### 5. 任务材料

包括 PDF、Word、Excel、图片、数据、网页、知识库、聊天记录和用户提供的事实。

材料决定模型能依据什么事实工作。

但“文件已经上传”不等于模型在所有系统里都一定逐字完整读过整份文件。

具体处理方式可能包括：

- 整篇读取；
- 分段；
- 检索；
- 表格工具解析；
- 多模态读取；
- OCR；
- 其他平台内部处理。

因此重要任务应明确：

- 文件名；
- 重点章节；
- 表格或页码；
- 希望提取的字段；
- 不足时怎么办。

### 6. 工具说明

工具说明告诉模型：

- 能搜索什么；
- 能读哪些文件；
- 能否执行代码；
- 能否修改表格；
- 能否发送、发布、购买或写入外部系统。

Prompt 只能表达“需要做什么”。

工具是否真的能做，还取决于工具是否存在、当前权限、运行环境、安全规则以及是否需要额外确认。

### 7. 工具结果

搜索、代码、文件或其他外部工具执行后，会返回网页结果、数据、文件内容、计算结果、错误和写入状态。

Agent 再基于这些结果决定下一步。

这形成一个典型循环：

~~~text
理解任务
↓
决定动作
↓
调用工具
↓
读取结果
↓
重新判断
↓
继续 / 修正 / 请求确认 / 完成
~~~

这就是 Agent 工作流中最基本的执行循环。

## 三、上下文窗口是“容量”，不是“已经读过的全部资料”

上下文窗口可以简单理解为：

> 当前一次模型推理能够接收和处理的信息容量。

但容量很大并不代表：

- 所有历史都自动在里面；
- 所有上传文件全文都自动在里面；
- 所有知识库文件都自动在里面；
- 所有 Skill 都一次性被加载。

长期使用中真正应该关心的是：

> **当前任务真正需要的有效上下文有没有被送进来。**

因此，与其无限增加 Prompt 长度，更重要的是：

- 当前目标是否明确；
- 旧条件是否清理；
- 必要材料是否被检索；
- 当前步骤是否只带相关规则；
- 工具结果是否已经纳入下一步。

## 四、上传文件时，要同时说明“读什么”和“为了什么”

文件只是材料，不是任务。

“总结这个 PDF”经常会得到平均分配篇幅的概括。

更清楚的任务应该说明：

- 读哪份文件；
- 重点看哪一部分；
- 为谁准备；
- 最终用途；
- 需要提取什么；
- 缺少信息时怎么处理。

例如：

~~~text
阅读这份年度运营报告。
目标：为明天的 10 分钟内部分享做准备。
重点关注第 3 章和附表 2。
只提取：
1. 报告提出的主要问题；
2. 支撑问题的关键数据；
3. 报告最终结论。
每个发现保留页码或来源位置。
材料没有提及的内容明确写“未提及”，不要补充。
~~~

真正起作用的不是“Prompt 更长”，而是它给出了：

> **阅读范围 + 阅读目的 + 提取标准 + 缺失信息处理方式。**

## 五、RAG / 知识库的本质是“先检索，再回答”

使用知识库时，模型通常不是每次都读取全部文件。

更常见的逻辑是：

~~~text
用户问题
↓
检索相关内容
↓
取回命中的片段
↓
模型基于片段回答
~~~

这会带来几个典型问题：

- 问题太宽，检索结果也发散；
- 切片打断表头、上下文或脚注；
- 新旧版本同时命中；
- 结果相关，但证据仍不够完整；
- 关键资料可能没有被检索到。

因此使用知识库时，Prompt 除了问题本身，还可以给出：

- 时间范围；
- 版本优先级；
- 来源优先级；
- 冲突处理规则；
- 缺证据时的处理方式。

例如：

~~~text
优先采用当前有效版本。
如果同一规则同时检索到新旧版本，保留版本日期，并以最新正式版本作为当前规则。
证据不足时不要补齐结论，明确列出缺口。
~~~

这与 [[LLM维护型个人知识库：从RAG到持续演化的Wiki]] 的知识架构相互补充：

- RAG 负责找到本轮相关证据；
- 持续演化 Wiki 负责把已经吸收过的长期知识保存下来。

## 六、搜索结果只是证据候选，不应直接等于结论

联网搜索通常也是一条执行链：

~~~text
生成查询
↓
搜索返回候选网页
↓
读取来源
↓
比较证据
↓
形成结论
~~~

搜索任务最好提前明确三个维度。

### 1. 搜什么

包括：

- 产品；
- 地区；
- 时间；
- 指标；
- 版本；
- 事件范围。

### 2. 哪些来源优先

例如：

~~~text
官方文件
> 原始数据 / 财报 / 论文
> 高质量专业机构
> 可靠媒体
> 二次转载
> 社区与个人经验
~~~

具体顺序应根据领域调整。

### 3. 来源冲突时怎么办

不要为了得到一个漂亮数字而强行平均。

应该：

- 保留不同口径；
- 标明时间；
- 解释差异可能来自什么；
- 在证据不足时保持不确定性。

## 七、Skill 的价值不是“让模型自动变专业”，而是保存可重复流程

对于一次性任务，清晰 Prompt 通常已经够用。

当同类任务不断重复时，可以把稳定部分抽出来。

### Prompt 更像

> 这一次要做什么。

### 模板更像

> 同类任务里固定不变的任务结构。

### Skill 更像

> 这种工作通常怎样执行，包括流程、工具、参考、脚本、验收和暂停点。

因此可以采用以下升级路径：

~~~text
一次性任务
→ 清晰 Prompt

重复任务
→ Prompt 模板 + 变量

稳定流程 + 文件 + 工具 + 脚本 + 验收
→ Skill
~~~

Skill 是否会被自动发现、什么时候加载、加载多少内容，都属于具体 Agent 平台的实现细节。

长期应该保留的是：

> **把已经验证有效的工作流程，从聊天里的临时指令升级成可复用资产。**

这与 [[Agent Native团队：多Agent协作与人机分工]] 中“把一次成功做法变成 Skill / 规则 / 知识”的原则一致。

## 八、工具调用不是一句“请调用工具”就会发生

假设你要做采购清单。

一句：

> 帮我根据去年的清单做今年采购表。

即使系统具备搜索和表格工具，也仍然存在大量不确定性：

- 去年哪些数量继续沿用；
- 哪些商品需要更新；
- 去哪里查价格；
- 采用什么规格；
- 如何处理价格冲突；
- 预算上限是多少；
- 允许不允许下单。

更可执行的任务链应该明确成：

~~~text
读取旧表
↓
识别需要更新的商品
↓
联网查价
↓
记录来源和查询时间
↓
计算分类小计与总额
↓
标记超预算 / 规格不明 / 价格冲突
↓
生成新文件
↓
等待人工确认
~~~

然后明确权限：

~~~text
允许：
- 读取
- 查询
- 计算
- 生成文件

禁止：
- 下单
- 付款
- 未经确认发送
~~~

Prompt 的职责不是“强迫某个工具执行”，而是：

> **把任务路径、条件、边界和终点写清楚，让 Agent 能判断何时应该使用工具。**

## 九、复杂任务可以用八个模块检查

来源提出了一套实用的八模块框架。

它比传统“角色 + 背景 + 任务 + 格式”更适合复杂 Agent 工作。

### 1. 任务结果：最终交付什么

需要写清：

- 交付物；
- 谁使用；
- 用于什么；
- 要支持哪个决定。

弱：

> 写一份竞品报告。

强：

> 给产品负责人准备一份 5 分钟可读完的竞品简报，用来判断下季度优先开发哪项功能。

### 2. 业务背景：模型还不知道什么

包括：

- 当前项目情况；
- 目标读者；
- 已有结论；
- 时间；
- 预算；
- 业务限制；
- 角色视角。

与其写“你是世界顶级营销大师”，不如写“站在社区烘焙店主理人的位置，为周边写字楼上班族设计活动，预算上限为 2 万元”。

一个重要原则：

> **具体工作位置和真实约束，通常比夸张角色头衔更有用。**

### 3. 核心指令：这次到底做哪些动作

使用可以直接对应交付过程的动词：

- 提取；
- 核对；
- 比较；
- 计算；
- 改写；
- 生成；
- 修改；
- 执行；
- 验证。

不要让模型只知道你“想要一个不错的结果”。

### 4. 输入材料：依据什么完成

列出文件、数据、图片、知识库、网页、用户事实和历史结论。

材料较多时提供导航锚点：

- 文件名；
- 章节；
- 页码；
- 表格；
- 字段；
- 时间段。

同时区分：

~~~text
事实依据
≠
风格参考
~~~

不能因为一篇样稿写得好，就把样稿里的事实复制进新任务。

### 5. 事实与权限边界：什么能做，什么不能做

包括：

- 时间范围；
- 数据口径；
- 预算；
- 信源优先级；
- 禁止事项；
- 工具权限；
- 人工确认节点。

负向限制不需要无限扩张。

更值得写的是：

> 一旦违反就会让任务失效的边界。

例如：

- 不得虚构数据；
- 不得覆盖原文件；
- 不得未经确认发送；
- 不得下单付款；
- 无法确认的事实必须标记。

### 6. 执行流程：先做什么，再做什么

复杂任务最好分阶段。

例如：

~~~text
第一阶段：读取资料 + 列出缺口
↓
人工补充
↓
第二阶段：形成结构 / 大纲
↓
确认
↓
第三阶段：正式生成
↓
第四阶段：事实与质量检查
~~~

这样做的核心价值是：

> **让错误尽量在便宜的阶段暴露。**

### 7. 输出形式与示例：结果应该长什么样

说明：

- 篇幅；
- 章节；
- 表格字段；
- 语言风格；
- 文件格式；
- 输出对象。

如果手里有真正满意的样例：

> 一个高度相关的好样例，通常比十几个抽象风格形容词更有价值。

但样例只用于结构、节奏、质量标准和表达方式。

样例中的事实不能自动转移到新任务。

### 8. 验收标准：怎样判断真的完成

这是复杂 Prompt 里最容易被漏掉的一层。

验收可以包括：

- 数据可追溯；
- 链接可以打开；
- 预算合计正确；
- 表格计算正确；
- 文件可以正常打开；
- 代码通过测试；
- 结论与证据对应；
- 没有遗漏要求；
- 列出仍需人工确认的项目。

没有验收标准时，AI 很容易把“我已经输出了一份内容”误当成“任务已经完成”。

---

## 十、八模块通用模板

复杂任务可以用下面的结构快速检查，而不是每次机械全文照抄。

~~~text
【任务结果】
最终要交付什么？
给谁使用？
要支持哪个决定或下一步动作？

【业务背景】
当前情况是什么？
目标对象是谁？
已有结论、时间、预算和现实限制是什么？

【核心指令】
请完成哪些明确动作？
需要提取、比较、计算、改写、修改、生成还是验证什么？

【输入材料】
可以使用哪些文件、数据、知识库、网页和已知事实？
重点读取哪些位置？
哪些是事实依据，哪些只是风格参考？

【事实与权限边界】
时间和数据口径是什么？
信源冲突时怎样处理？
哪些操作禁止？
做到哪一步必须暂停并请求确认？

【执行流程】
先做什么，再做什么？
哪些阶段需要先返回中间结果？

【输出形式与示例】
篇幅、结构、字段、语气、文件格式是什么？
是否有高度相关样例？

【验收标准】
交付前逐项检查什么？
哪些事实仍然需要人工确认？
~~~

使用规则：

- 简单任务：直接写清动作；
- 中等任务：选最关键的 3–5 项；
- 高成本 / 高风险 / 多工具任务：完整展开。

---

## 十一、五个词可以作为最小检查框架

如果不想记八个模块，可以只记：

> **结果、材料、边界、动作、验收。**

- 结果：我要什么成品？
- 材料：依据什么完成？
- 边界：哪些条件不能错？
- 动作：模型和工具具体要做什么？
- 验收：什么才算真的完成？

只要这五项足够清楚，大多数复杂任务已经比“万能提示词”更接近真实工作说明书。

---

## 十二、写作任务先补事实，再下判断，最后润色

当文案看起来“AI味很重”时，不要一上来就要求：

> 写得更像人。

模型很可能只是增加口头语、故意打乱句子、加一些看似生活化的细节，或者把机器腔藏得更深。

更可靠的顺序是：

~~~text
补真实事实
↓
确认作者观点与取舍
↓
检查逻辑
↓
最后做语言编辑
~~~

---

## 十三、第一轮先检查“这篇内容里有没有人”

在语言层面返工之前，先问：

1. 有没有只有作者自己才能提供的经历、观察或数据？
2. 作者到底赞成什么、反对什么、建议先做什么？
3. 抽象判断后面有没有具体场景？
4. 所谓收益要付出什么时间、预算或学习成本？
5. 删除一段以后，读者会不会损失新信息？

这一步不能完全外包给 AI。

AI 可以指出哪些地方缺事实、哪些判断太抽象、哪些内容没有证据，但它不能凭空制造作者真实经历。

因此：

> **“编一个真实故事”不是解决 AI 味的方法，而是在制造更难识别的虚构。**

---

## 十四、第二轮再做“语言手术”

AI 更适合在事实和观点已经稳定后做编辑。

可以让它逐段检查：

- 无信息增量的正确废话；
- 高频套话；
- 空泛形容词；
- 公关腔；
- 句式重复；
- 段落跳跃；
- 缺少人物、时间、数字、动作、成本和结果的抽象判断；
- 回避选择的表达；
- 缺乏来源的数据和引用。

一个安全的工作流是：

~~~text
先诊断
↓
列修改清单
↓
作者补事实
↓
再重写
~~~

而不是直接整篇洗稿。

因为整篇重写很容易把作者自己的原话、已经确认的数据、个人判断和表达辨识度一起抹掉。

---

## 十五、资料总结：不要平均总结，要围绕用途取舍

同一份长报告，可以产生完全不同的“好总结”。

如果任务只是“帮我总结”，模型自然倾向于每章说一点、尽量覆盖、平均分配篇幅。

如果任务是“为明天 10 分钟分享找出最值得讲的 3 个发现”，则模型需要做筛选、排序、删除和围绕听众重组。

因此摘要质量往往取决于：

> **你有没有告诉模型“这份摘要要用来干什么”。**

---

## 十六、聊天记录整理：必须区分“建议、待确认、已决定”

会议、群聊和长对话最容易发生状态误判。

典型错误：

> 把“有人建议做 X”写成“团队决定做 X”。

因此提取行动项时应显式定义状态口径。

例如：

| 字段 | 说明 |
| --- | --- |
| 事项 | 已明确要推进的任务 |
| 负责人 | 明确出现的人 |
| 截止时间 | 原记录明确给出的时间 |
| 当前状态 | 已确认 / 待确认 / 有分歧 |

如果没有负责人，不应自行指定。

如果仍有争议，应单独列出，不让 AI 替团队做决定。

---

## 十七、同一事实面向不同受众，需要重新组织信息

“润色一下”经常不够。

至少需要知道：

- 发给谁；
- 他们最关心什么；
- 他们需要做什么；
- 哪些细节该保留；
- 哪些背景可以省略。

例如同样是“项目延期”：

### 给客户

优先：

- 延期事实；
- 补救动作；
- 新交付时间；
- 责任表达。

### 给内部团队

优先：

- 阻塞原因；
- 谁今天完成什么；
- 当前依赖；
- 风险节点。

内容源可以相同，但：

> **使用对象改变后，信息顺序和粒度也应该改变。**

---

## 十八、计划类任务先给现实约束，再让模型做减法

“帮我安排两天旅行”很容易得到热门景点、推荐餐厅和很满的时间表。

真正影响方案可执行性的却是：

- 从哪里出发；
- 预算；
- 同行人数；
- 饮食限制；
- 行动能力；
- 交通方式；
- 天气；
- 是否接受排队；
- 实时营业时间。

计划任务的价值不在“列得多”，而在：

> **在真实约束下做取舍。**

当价格、营业时间、票务或天气具有时效性时，再触发搜索与实时核验，而不是凭静态知识补齐。

---

## 十九、表格任务：让工具处理完整数据，让模型解释结果

不要把几行样本贴进聊天框后要求“帮我看看整张表有什么问题”。

更可靠的流程是：

1. 用表格 / 数据工具读取完整工作表；
2. 报告总行数；
3. 检查空值；
4. 检查重复；
5. 检查金额或字段异常；
6. 按指定口径计算；
7. 模型解释异常；
8. 原文件保持只读；
9. 结果另存；
10. 统计口径先确认，再生成最终版本。

核心是：

> **模型负责理解与解释，计算工具负责完整遍历与确定性运算。**

---

## 二十、真正需要优化的是返工率，而不是 Prompt 长度

复杂 Prompt 写得很长，不代表任务效率高。

可以追踪四个更有用的指标：

- 第一次输出有多少可以保留；
- 需要补充几轮信息；
- 人工修改用了多久；
- 最终是否通过验收。

这比“Prompt 有多少字”更接近真实生产效率。

---

## 二十一、复杂任务适合三回合工作法

### 第一回合：确认任务

先让 AI 检查目标、材料、限制、缺口，以及哪些问题会显著改变结果。

只问真正影响方向的问题，例如：

- 预算差十倍；
- 受众完全不同；
- 是否公开发布；
- 是否允许联网；
- 是否允许修改原文件。

这类问题应该尽早确认。

### 第二回合：生成交付

范围确认后再读资料、调工具、生成文件、写正文和批量执行。

长项目可以先做一个最小样本。

例如课程生产：

> 先写一课，确认结构和难度，再批量生成剩余课程。

### 第三回合：验收

检查数字、来源、结构、文件、遗漏、权限、事实，以及是否满足原始目标。

AI 可以自查，但关键业务数据、专业结论、个人经历、高风险决策和对外发布仍应保留必要的人类确认。

---

## 二十二、不满意时，不要只说“重写一版”

“再写一版”通常只是重新采样。

原问题可能换一种形式继续存在，已经正确的内容也可能被一起改坏。

更有效的返工反馈有四个要素：

1. 哪一段有问题；
2. 违反了什么标准；
3. 哪些部分必须保留；
4. 下一版具体改什么。

例如：

~~~text
保留第一部分的数据和第三部分行动清单。
只修改第二部分。

问题：
1. 句式过度使用“首先、其次、最后”；
2. “提升效率”没有具体动作；
3. 缺少附件中的真实案例。

修改：
- 用附件中的相关材料补充一个具体场景；
- 材料没有效果数据的地方标记“待补充”；
- 修改后列出删掉了什么、新增了什么、还需要确认什么。
~~~

这与生成式工作流里的“局部返工、锁定已正确部分”是同一原则。

---

## 二十三、从 Prompt 到模板，再到 Skill

可以根据任务成熟度选择不同载体。

| 情况 | 合适形式 |
| --- | --- |
| 一次性、低风险任务 | 直接 Prompt |
| 周期性重复任务 | Prompt 模板 |
| 稳定 SOP | 模板 + 检查清单 |
| 需要文件、工具、脚本、权限和多阶段执行 | Skill / Agent workflow |
| 多人或长期复用 | Skill + 版本 + 测试案例 + 权限规则 |

不要因为“Skill 更高级”就把所有任务都包装成 Skill。

判断标准是：

> **这套流程是否已经稳定到值得长期复用。**

---

## 二十四、一个更完整的复杂任务执行循环

把全文的方法组合起来，可以形成：

~~~text
明确结果
↓
补充业务背景
↓
写清核心动作
↓
指定材料与证据角色
↓
定义事实边界与权限
↓
判断是否需要工具
↓
拆执行阶段
↓
先处理会改变方向的问题
↓
执行 / 调用工具
↓
读取工具结果
↓
局部修正
↓
形成交付
↓
按验收标准检查
↓
列出剩余不确定项
↓
人工确认高风险内容
↓
稳定流程沉淀为模板 / Skill
~~~

这套流程与 [[Agent Native团队：多Agent协作与人机分工]] 中的“目标 → 拆解 → 执行 → 验证 → 人工升级”属于同一个底层逻辑。

区别只是本文把它落到了 Prompt、文案、材料、工具、RAG、文件任务和返工这些更具体的操作层面。

---

## 二十五、常见误区

### 误区 1：Prompt 越长越专业

错误。长度只有在增加有效约束时才有价值。

### 误区 2：复杂任务必须套固定万能公式

错误。简单任务应该简洁；复杂任务才逐步展开。

### 误区 3：给了角色设定，模型就会自动更专业

角色只是视角约束。它不能创造不存在的工具、数据、权限或领域事实。

### 误区 4：上传文件等于模型完整掌握文件

错误。具体读取与检索方式依赖系统实现。重要材料应明确导航位置和任务目的。

### 误区 5：知识库等于全量资料自动进入上下文

错误。RAG 通常只提供本轮命中的相关片段。

### 误区 6：搜索到网页就等于已经核验

错误。搜索结果仍需要比较来源、时间、口径和证据质量。

### 误区 7：写“请调用工具”就一定会调用

错误。工具使用取决于任务需求、工具存在、权限、当前执行阶段与安全确认要求。

### 误区 8：去掉几个“AI词”就去掉了 AI 味

错误。真正需要补的是事实、场景、取舍、成本、动作和作者判断。

### 误区 9：AI 应该一次直接交付最终成稿

对于高成本复杂任务，先确认方向往往更省时间。

### 误区 10：输出了文件就等于完成

没有通过验收，任务仍然没有真正结束。

---


## 二十六、AI 应用的四层能力与故障诊断

对于初学者，与其先记产品名，不如先判断 AI 正在承担哪一层工作。

### 1. 四类常见能力

| 层级 | 典型任务 | 主要检查点 |
| --- | --- | --- |
| 理解与表达 | 解释概念、比较方案、澄清问题 | 是否准确理解问题，概念是否被误解 |
| 生成内容 | 文章、邮件、图片、脚本、代码 | 事实、格式、可用性和生成错误 |
| 处理已有材料 | 总结 PDF、比较合同、整理会议、修改文件 | 是否保留原数字、结构、状态和真实意图 |
| 调用工具执行动作 | 搜索、读取系统、运行程序、创建或修改文件 | 权限、真实执行结果、写入范围和审计 |

能力叠加越多，验收点也越多。

例如“读产品资料 → 总结 → 生成文章 → 创建文件”同时涉及材料读取、内容生成和外部写入，不能只检查最后一段文字是否通顺。

### 2. AI 做不好任务时，先分清是哪种故障

常见问题可以优先排成四类：

1. **任务不清楚**：例如只说“优化一下”，但没有目标和标准；
2. **材料不够**：任务依赖项目文档、历史结果或用户反馈，却没有提供；
3. **信息在模型当前环境之外**：需要最新网页、实时库存、私人文件或业务系统数据；
4. **缺少验收**：代码没有运行、文件没有打开、数字没有核对、事实没有回到来源。

对应修复方式是：

~~~text
任务模糊 → 补目标与动作
材料不足 → 补上下文和证据
信息在外部 → 调用合适工具
结果不稳定 → 增加验收和人工确认
~~~

这比不断“优化提示词措辞”更接近真实问题。

### 3. API、工具、MCP 与 Agent 分别解决什么

这几个词经常被产品宣传混在一起，可以用功能关系理解：

- **API**：系统对外暴露的接口约定，说明可以请求什么、需要什么参数、会返回什么；
- **工具（Tool）**：当前 AI 运行环境实际可以调用的一项能力，背后可能使用 API，也可能读取本地文件或运行程序；
- **MCP**：把外部能力和上下文以相对统一方式提供给兼容 AI 客户端 / Agent 的协议与接入方式之一；它不自动解决工具质量、账号认证、权限和业务边界；
- **Agent**：围绕目标反复执行“判断 → 选择工具 → 读取结果 → 再判断”的工作方式。

因此不要因为接入了 MCP 就假设：

- 工具一定可靠；
- 数据一定最新；
- 权限已经合理；
- Agent 一定会选择正确工具；
- 写入动作不需要人工边界。

### 4. 可靠性来自四层边界共同工作

一个更稳的 AI 任务通常同时依赖：

1. **提示词 / 任务说明**：明确目标、动作、边界和完成标准；
2. **上下文 / 材料**：提供真实业务信息和证据；
3. **权限**：限制 AI 实际能够读取、修改、发送或删除的范围；
4. **验收**：检查文件、Diff、运行结果、来源和最终成品。

“请小心操作”不能替代最小权限和写后检查。

尤其对外部写入动作，更稳的升级顺序通常是：

~~~text
先读取
→ 再允许生成草稿
→ 人工确认
→ 再开放有限写入
~~~

### 5. 流程至少真实使用几次，再沉淀成 Skill

一次性任务通常不值得马上包装成 Skill。

当一套流程已经真实执行两三次，并逐渐稳定下来时，再检查：

- 输入是否稳定；
- 步骤是否稳定；
- 失败条件是否清楚；
- 输出格式是否固定；
- 哪些地方必须停下来问人；
- 是否存在可以交给脚本完成的确定性检查。

如果每次都还在大幅改方法，它仍然处于探索阶段；如果已经反复复制同一套 Prompt、模板和检查表，就开始具备 Skill 化价值。

---

## 二十七、如何把这套方法应用到 NoIT

NoIT 本身可以视为这套复杂任务方法的一个具体实例。

用户提供资料后，并不是：

~~~text
附件
→ 总结
→ 结束
~~~

而是：

~~~text
【任务结果】
把资料变成可长期使用的 NoIT 知识

【业务背景】
仓库有固定规则、目录和已有知识

【核心指令】
读取、核验、去重、融合、更新

【输入材料】
用户新资料 + 仓库现有文件 + 必要外部来源

【边界】
不重复建笔记、不写过时信息、不把不确定内容伪装成事实

【执行流程】
读规则 → 读现有主题 → 判断增量 → 更新 / 新建 → 更新导航

【输出】
Markdown 知识主体

【验收】
脱离原资料仍可理解，来源可追溯，仓库无明显重复
~~~

因此 NoIT 的核心其实也是：

> **把一次聊天要求，变成可复用、可验收、可持续维护的工作系统。**
