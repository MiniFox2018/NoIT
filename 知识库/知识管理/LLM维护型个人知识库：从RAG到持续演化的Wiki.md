# LLM维护型个人知识库：从RAG到持续演化的Wiki

## 核心问题

传统“把文件交给 AI 再提问”的工作方式，通常接近 RAG：

1. 保存一批原始资料；
2. 每次提问时重新检索相关片段；
3. LLM 临时把这些片段拼起来回答；
4. 对话结束后，这次综合出的理解通常不会自动沉淀成长期资产。

这种模式适合“从资料里找答案”，但存在一个长期问题：

> 同样的知识关系、矛盾、对比和综合结论，可能每次提问都要重新发现。

当资料越来越多，而且真正有价值的问题需要跨多篇资料综合时，重复检索与重复推理会越来越明显。

一种不同的思路是：让 LLM 不只负责检索，而是持续维护一个**长期存在、不断演化的知识 Wiki**。

每加入一个新来源，AI 不只是给它生成摘要，而是：

- 找到已有相关主题；
- 更新现有主题页；
- 补充实体、概念和方法；
- 记录新旧资料之间的冲突；
- 修正被新资料推翻的旧结论；
- 建立页面之间的关联；
- 把新的综合判断写回知识库。

这样，知识被“编译”一次后持续保留，而不是每次查询时重新从原始资料里临时拼装。

---

## 一、RAG 与持续演化 Wiki 的区别

| 维度 | 传统 RAG / 文件问答 | LLM 维护型 Wiki |
| --- | --- | --- |
| 核心资产 | 原始文档 | 持续更新的知识页面 |
| 新资料进入 | 建索引 | 与已有知识融合 |
| 重复知识 | 查询时再处理 | 入库时去重 |
| 矛盾 | 查询时临时发现 | 长期记录并维护 |
| 跨来源综合 | 每次重新生成 | 综合结果持续积累 |
| 历史问题的高价值回答 | 容易留在聊天中 | 可以反写为知识 |
| 维护方式 | 人工整理较多 | AI 承担大量维护工作 |

两种模式并不是互斥的。

更合理的组合通常是：

- 原始资料或外部网页负责提供证据；
- Wiki 负责保存已经吸收后的长期知识；
- 搜索或 RAG 用于补充新证据和处理尚未吸收的资料。

## 二、三个逻辑层

Karpathy 提出的模式可以拆成三个逻辑层：

### 1. 来源层

包括文章、论文、图片、数据文件、书籍、会议记录等。

作用是提供可追溯依据。

### 2. 知识层

由 Markdown 页面组成，包括：

- 主题页；
- 概念页；
- 实体页；
- 比较页；
- 方法页；
- 综合结论；
- 导航页。

AI 负责持续创建、修改、合并和维护。

### 3. 规则 / Schema 层

用一份明确的项目规则告诉不同 AI：

- 目录怎样组织；
- 页面怎么命名；
- 什么情况下新增页面；
- 什么情况下更新旧页面；
- 如何处理重复；
- 如何标记来源；
- 如何处理冲突；
- 如何维护索引；
- 什么内容必须人工确认。

这层非常重要，因为没有统一规则时，不同模型或不同会话很容易产生不同的分类、命名和处理习惯。

在 Codex 等 Agent 环境里，可以使用 `AGENTS.md`；Claude Code 常见的是 `CLAUDE.md`。平台名称不是重点，关键是：

> 把稳定方法写进仓库，而不是依赖某次聊天的上下文记忆。

NoIT 已经采用了这一原则：根目录的 `PROJECT_RULES.md` 保存长期规则，`AGENTS.md` 作为 AI 入口。

## 三、知识入库（Ingest）应该发生什么

一个成熟的入库流程不应该是：

```text
新文章
→ 生成摘要
→ 新建一篇笔记
```

更合理的是：

```text
新来源
→ 完整读取
→ 检查现有知识
→ 判断重复 / 新增 / 冲突 / 过时
→ 更新一个或多个已有主题
→ 必要时新增主题
→ 更新索引
→ 记录来源和本次变化
```

一篇来源完全可能同时影响多个知识主题。

例如，一篇关于 AI 学习方法的文章可能同时补充：

- AI 辅助学习；
- 项目驱动学习；
- 输出驱动学习；
- 知识验证；
- AI 与人的分工。

真正的知识系统应该围绕“主题关系”维护，而不是围绕“文章来源”维护。

---

## 四、查询结果也可以继续沉淀

长期知识系统还有一个容易忽略的来源：**用户自己提出的问题**。

有些高价值内容并不是来自某篇原始文章，而是在多轮讨论中形成的，例如：

- 两种方法的系统比较；
- 某个问题的完整决策框架；
- 从多份资料中得到的新联系；
- 对已有知识的重新分类；
- 一套经过实践验证的新流程。

如果这些结果只留在聊天记录里，它们仍然会丢失。

因此，一个好的规则是：

> 当一次问答形成了可长期复用的新知识时，应该允许把最终结果反写进 Wiki。

这样，系统不仅通过“新增来源”增长，也通过“思考和提问”增长。

## 五、索引和日志是两种不同东西

Karpathy 特别区分了 `index.md` 和 `log.md`。

### index：内容导航

索引回答：

> 现在知识库里有什么？

可以记录：

- 页面链接；
- 一句话说明；
- 所属类别；
- 状态；
- 更新时间；
- 必要时记录来源数量。

它服务于**当前知识结构**。

### log：演化历史

日志回答：

> 这个知识库什么时候发生了什么变化？

可以记录：

- 新来源被吸收；
- 哪个主题被更新；
- 做过哪些健康检查；
- 哪次查询产生了新知识；
- 哪个旧结论被新资料替代。

它服务于**时间线和维护追踪**。

两者不能互相替代。

对于小型仓库，README 或目录本身可以暂时代替 index；只有当规模开始明显增长时，再独立建立 `index.md` 和 `log.md`，避免过早增加结构复杂度。

## 六、定期 Lint：知识库也需要“体检”

代码需要 lint，长期知识库也需要。

周期性健康检查可以寻找：

### 1. 冲突

两个页面是否对同一事实给出了不同结论？

### 2. 过时信息

某个旧结论是否已经被更高质量的新来源替代？

### 3. 孤立页面

有没有页面几乎没有任何关联？

### 4. 重复主题

是否出现多个名称不同但实质相同的页面？

### 5. 缺失主题

某个重要概念是否被很多页面反复提到，却没有自己的完整说明？

### 6. 断裂关系

已有页面之间是否应该建立链接却没有建立？

### 7. 来源缺口

重要结论是否缺少足够可靠的来源或时效核验？

这类工作非常适合 AI，因为它机械、重复、需要跨文件检查，但又不一定值得人逐页维护。

## 七、什么时候需要搜索引擎或向量检索

在知识库规模较小时，没有必要一开始就建设复杂的向量数据库。

如果只有几十到几百个 Markdown 页面，常见方法已经可以工作：

- 目录结构；
- index；
- 文件名；
- 全文关键词搜索；
- Obsidian 链接；
- GitHub 搜索；
- AI 直接读取相关文件。

规模进一步扩大后，可以再加入：

- BM25；
- 向量检索；
- Hybrid Search；
- LLM reranking；
- MCP 搜索接口。

一个重要原则是：

> 不要为了“看起来像知识系统”而过早建设检索基础设施。

先确认普通文本搜索真的成为瓶颈，再升级。

Karpathy 在原文中提到 `qmd` 作为本地 Markdown 混合搜索的一种可选实现，但这属于工具选择，不是架构本身的必要条件。

## 八、Obsidian 为什么适合这种架构

这种知识系统天然适合 Markdown + Obsidian：

- 页面就是普通 `.md` 文件；
- Git 可以做版本历史；
- 双向链接可以表达知识关系；
- Graph View 可以观察知识网络；
- Frontmatter 可以保存结构化元数据；
- 本地文件长期可迁移；
- AI Agent 可以直接读写。

可以把它理解成：

> Obsidian 是知识库的浏览与编辑界面，AI Agent 是维护者，Git 仓库是长期保存层。

但知识库不能依赖某个 Obsidian 插件才能理解。

插件适合做增强，不应该成为知识本身的前提。

## 九、人的职责与 AI 的职责

这类系统最重要的不是“让 AI 全自动”，而是正确分配职责。

### 人更适合负责

- 决定什么资料值得进入；
- 确定长期关注方向；
- 提出真正有价值的问题；
- 判断哪些结论重要；
- 对高风险或主观判断进行最终确认；
- 发现新的研究方向；
- 决定知识系统最终服务什么目标。

### AI 更适合负责

- 阅读大量资料；
- 去重；
- 比较；
- 交叉引用；
- 文件整理；
- 更新旧页面；
- 找冲突；
- 找孤立页面；
- 维护索引；
- 检查格式与一致性；
- 保存来源；
- 执行重复性的知识维护工作。

这和 [[Agent Native团队：多Agent协作与人机分工]] 中的人机分工存在同一个底层逻辑：

> 人负责方向、判断和验收；Agent 承担可以规模化执行的认知与维护工作。

## 十、Karpathy 模式与 NoIT 的差异

Karpathy 的原始方案建议将“原始来源”作为单独、不可修改的资料层长期保存。

NoIT 当前采用的是更轻量的取舍：

### NoIT 不要求机械保存所有原始文件

很多公开网页、文章、工具和在线资料只需要保留：

- 来源名称；
- 原始 URL；
- 作者 / 平台；
- 发布时间；
- 处理日期；
- 必要的版本信息。

如果资料具有下面特征，则再考虑保留原始文件：

- 原网页可能消失；
- 版本变化非常快；
- 未来需要精确引用；
- 来源无法稳定访问；
- 用户明确要求保留。

### NoIT 的正式知识必须更完整

即使不保存全部原始文件，吸收后的 Markdown 仍要尽量达到：

> 后续不需要回原网页，就能理解该主题所需的主要知识。

这也是 NoIT 与纯链接收藏、纯 RAG 文件库之间最重要的区别。

## 十一、NoIT 可以借鉴的架构

结合当前项目，更适合 NoIT 的结构是：

```text
用户提供来源
      ↓
AI 读取和核验
      ↓
PROJECT_RULES.md / AGENTS.md
      ↓
检查已有主题
      ↓
去重 / 融合 / 修正 / 建立关联
      ↓
知识库/*.md
      ↓
README / 后续 index
      ↓
周期性知识库体检
```

这里最值得长期保留的不是某个特定工具，而是一条原则：

> **知识应该持续编译，而不是持续堆积。**

新增十个来源，不一定新增十篇知识页面。

真正理想的结果是：

- 来源越来越多；
- 知识越来越完整；
- 重复越来越少；
- 结构越来越稳定；
- 查询越来越依赖已经沉淀的知识，而不是每次重新阅读全部来源。

## 十二、BRAIN.md：把“当前结论”和“演化历史”拆开

MindMux 的 BRAIN.md 项目把 LLM Wiki 思路进一步应用到“项目记忆”。

它最值得借鉴的不是具体 CLI，而是一个简单的数据模型：

```text
compiled_truth
= 当前应该被后续 Agent 直接使用的最好结论

timeline
= 这个结论如何形成、被什么证据支持、什么时候反转
```

这解决了知识维护里的一个长期矛盾：

- 如果只保存最新结论，历史依据容易丢失；
- 如果每次都保存全部过程，新 Agent 又需要重复阅读大量旧上下文。

把两者分开后，日常任务只需要加载当前结论；需要审计、理解反转或重新决策时，再回看时间线。

### 对 NoIT 的适用方式

NoIT 不需要机械地给每一篇知识页都增加完整 timeline。

当前更轻量的方案仍然更合适：

- 正文维护“当前最好理解”；
- Git 保存完整版本历史；
- 来源区保留证据与时间；
- 只有出现重要争议、版本反转或长期决策时，才显式记录变化理由。

这样既借鉴了 BRAIN.md 的“当前事实与历史证据分离”，又不会让普通知识笔记变成复杂的决策数据库。

另一个值得借鉴的原则是 **decision-grade memory**：

> 不是所有聊天内容都值得持久化；只有未来仍重要、且无法轻易重新推导的信息才应该进入长期项目记忆。

这与 NoIT “不保存所有来源副本，只保存真正长期价值”的原则一致。

详细工具说明见 [[BRAIN.md：项目级持久化记忆层]]。

## 十三、适合 NoIT 后续增加但暂不急于实现的能力

当仓库规模明显增大时，可以考虑：

1. 独立 `index.md`；
2. 追加式 `log.md`；
3. 定期 lint / health check；
4. 自动检查孤立页和重复主题；
5. 自动标记过时事实；
6. 本地全文或混合搜索；
7. 来源与知识页面之间更明确的 provenance；
8. 对高风险修改增加人工 review gate。

这些能力应在真实痛点出现后再增加，不需要一开始全部建设。

## 十四、从“上传文件”到正式知识库：什么时候值得升级

“资料多”本身不是建设知识库的充分理由。

更重要的是先区分四种信息层：

| 信息层 | 解决什么问题 | 典型例子 |
| --- | --- | --- |
| 当前上下文 | 这一次任务里 AI 现在能看到什么 | 当前 Prompt、附件、刚返回的工具结果 |
| 长期记忆 | 与用户或长期协作相关、未来可能继续影响回答的背景 | 稳定偏好、项目长期约定 |
| 知识库 | 会被反复查询、需要更新和追溯来源的资料 | 方法文档、研究资料、项目 Wiki |
| 实时数据 | 当前状态必须现查，旧文档不能代表现在 | 库存、订单、余额、实时价格、当前日程 |

最常见的错误，是把四者互相替代：

- 把一次上传文件误认为长期知识库；
- 把历史记忆当成事实数据库；
- 把几个月前的静态文档当成实时业务状态；
- 为一次性任务过早搭建 RAG。

### 用四个问题判断是否真的需要知识库

1. 这批资料会不会反复使用？
2. 内容会不会持续更新？
3. 回答是否必须回到来源和版本？
4. 不同人是否存在不同访问权限？

如果四项都很轻，一次上传文件、普通文件夹或一组整理清楚的 Markdown 往往已经够用。

随着复用、更新、来源和权限要求提高，再逐步增加：

- 正式目录和命名规则；
- 来源与版本元数据；
- 全文检索；
- RAG / 混合检索；
- 访问控制；
- 更新与失效机制。

### 个人系统可以从最小结构开始

对于尚未形成正式知识库的个人学习项目，可以先把材料分成：

~~~text
原始资料
已核验笔记
正在进行的项目
已完成的产出
~~~

这个结构的价值不是目录本身，而是把“证据、已吸收知识、当前工作和最终成果”区分开。

NoIT 不需要机械采用这四个实体目录，因为当前仓库已经有自己的知识层、资源层和 Git 历史。值得吸收的是：

> **先用最小结构解决真实检索和维护问题，等复杂度真的出现，再升级基础设施。**

## 十五、把发现、素材、证据与正式知识分层

Yichen Web Research 和 Chubby Skills 展示了两种互补的资料处理工程实现：前者调度互联网发现、已知链接归档、私人书签导出、音视频转录与证据综合；后者围绕 Markdown 素材库构建采集、搜索、带来源引用的资料包和可选 MCP 服务。

| 阶段 | 应保留的信息 | 必须分清的边界 |
| --- | --- | --- |
| 发现 | 关键词、平台、时间、候选 URL、搜索覆盖缺口 | 搜索摘要不是已核验事实 |
| 采集 | 来源 URL、作者、采集时间、正文/转录、失败状态 | 采集完成不代表内容合法可再分发 |
| 证据 | 具体主张和原始出处对应、反证、未解问题 | 原文能够打开不等于支持主张 |
| 入库 | 去重、主题归档、知识链条、时效与适用条件 | 保存素材不等于 NoIT 已吸收知识 |
| 调用 | 搜索结果、原文行号/时间码、引文与文件哈希 | 引文可追溯不保证来源观点正确 |

**建议沿用的最小契约**：`search`、`read`、`download`、`export private bookmarks`、`ingest`、`synthesize` 是不同动作；由任务显式授权独立控制，不能搜索成功后擅自下载，不能已登录浏览器就默认获准导出私人收藏。

实践中使用来源唯一标识、处理批次、内容哈希、失败清单和重试状态可解决重复入库与来源丢失；平台登录、反爬、ASR 和云端额度属于可替换适配层。Chubby 的本地内容库可充当 NoIT 的候选素材层，Yichen 的研究路由可参考其证据把关，但最终知识仍必须遵守 NoIT 的主题融合及逐章覆盖规则。本轮只核验项目文件，不代表端到端工具部署验收。

## 十六、X 书签后置整理：Jev 的结构化判断与复核边界

《用 Jev 管理 X 书签》的核心方法是**先零摩擦收藏，之后统一分类**：收藏时不强制决定目录，避免打断信息流；用已授权的导出/浏览器读取形成结构化书签清单，再做标签、后续动作与风险判断。原文区分本地脚本＋轻界面和 Codex/Grok Bot 浏览器操作两条路线；**Jev 模型本身不会自动登录 X 或采集私有书签**。

### 一套可以直接迁移的字段

| 字段 | 示例选项 | 作用 |
| --- | --- | --- |
| `bookmark_kind` | tip、case、opinion、noise | 区分实践方法、案例、观点与低信息量 |
| `topic_related` | true / false | 是否关联当前主题 |
| `next_step` | read、cite、archive、drop | 精读、引用候选、留档、建议舍弃 |
| `risk` | 低／中／高 | 事实、版权、隐私、名誉等公开引用风险 |

作者用 TypeSafe System One 模型 Jev 的 **Choice、Noul、Score** 在给定选项内返回结构化判断；可以用 Python SDK，前端可通过 Streamlit/Gradio 轻量展示。需要注意：输出标签固定不代表判断正确；模型的 confidence 不等于经统计校准的真实准确率。原文自述 8 条合成样本平均约 235ms、30 条真实书签分类平均约 219ms，均不足以证明在大规模中文书签上表现可靠。

### NoIT 的落地边界

```text
合法导出 X 书签或浏览器有权限读取
→ 保留原始 URL、时间、可获得的正文/媒介类型
→ 限定类别与下一步动作
→ 低置信度或高风险人工核对
→ 有长期价值的内容再进入 NoIT 全文读取、去重与核验流程
```

- 由于书签可能只保存链接而原帖会删除/变为不可访问，采集是否完整与内容是否授权再分发必须分开。
- 不根据 `drop` 自动永久删除仓库原有资源；资源与已吸收的知识独立判断，遵守 NoIT 删除保护。
- `cite` 仅代表引用候选，引用前还需回看源帖、原始材料、发布日期、语境与版权。
- 浏览器操作必须基于用户授权登录态，不把 Cookies、私信、私人信息或凭据交给不可信工具；第三方处理内容应评估隐私。
- 分类选项应与 NoIT 的现有工作流标签和知识/资源双轨规则映射，不新增与当前目录冲突的第二套分类。

2026-10-09 定向核对了 [TypeSafe 官网](https://typesafe.ai/) 的 Jev 结构化决策模型定位，未实际购买调用或独立复测性能。官方 [文档入口](https://docs.typesafe.ai/) 可用于后续核对 SDK/API；X 书签可用 [Twitter Web Exporter](https://github.com/prinsss/twitter-web-exporter) 作为另一种候选采集工具，它和 Jev 不是同一个服务。

## 来源补全的三个状态：取得、对应与吸收

资料抓取记录应分别回答：正文是否取得、片段属于哪个原帖或章节、知识是否已融入正式主题。返回非空文本只证明取到了内容，不能证明线程、媒体和引用完整，也不能证明所有观点正确。

批量补全时先保留原编号和原 URL，取得主帖、作者续帖、引用与文章嵌入实体；用返回 ID 校对请求目标。长文章用正文结构区分普通段落、代码/Markdown、链接、媒体和嵌入帖。Article 实体 ID 与发布帖 ID 保存映射；短链接和推荐卡片不能仅凭外观当成作者续帖。

独立知识融合以后，记录来源、章节/片段、承接主题、处置理由与证据边界。以文件校验值保证归档未变，以人工判断核对知识去向。格式校验不冒充语义阅读。全文和原始响应保存在本地或合法的私有位置；公开知识库保留来源和重新组织的知识，不公开大段镜像原文。
