# 低成本自举型SaaS：用简单架构换取更长跑道

## 核心判断

独立 SaaS 在 PMF 之前，技术架构首先应该帮助你：

- 更快上线；
- 更容易理解；
- 更容易排错；
- 保持低固定成本；
- 在用户真正出现后再扩展。

Steve Hanov 的低成本技术栈案例并不是“所有项目都应该用 Go、SQLite、单 VPS”。

真正值得长期吸收的原则是：

> **不要提前为尚不存在的规模付复杂度税。**

---

## 一、跑道不仅由融资决定，也由 burn rate 决定

创业跑道可以粗略理解为：

~~~text
可承受资金 ÷ 每月净消耗
~~~

提高融资是一种方式，降低固定成本同样可以延长试错时间。

对于小型自举项目，低 burn rate 会带来：

- 更少融资压力；
- 更少被增长目标绑架；
- 更多寻找 PMF 的时间；
- 更容易停止失败实验；
- 架构更容易保持可理解。

但不能为了省钱牺牲数据安全、备份、合规或核心可靠性。

---

## 二、复杂度是一种持续成本

基础设施的成本不只是账单，还包括：

- 配置时间；
- 部署时间；
- 监控；
- 升级；
- 故障排查；
- 安全维护；
- 认知负担。

如果一个人运营多个小产品，最重要的不是“架构先进”，而是：

> 半年后自己还能不能快速理解它为什么坏了。

因此，早期优先选择少组件、少依赖、少运维面的系统，通常比模仿大型互联网公司的架构更合理。

---

## 三、单机优先是一种阶段策略

Hanov 的实践从单 VPS 开始。

可抽象成一条策略：

1. 先选择能满足当前负载的最小部署单元；
2. 做好日志、备份、恢复和监控；
3. 观察真实瓶颈；
4. 只有瓶颈出现时再拆服务或升级资源。

“单机”不是永远不扩展，而是拒绝**预测式扩展**。

需要提前升级的例外包括：

- 明确的高可用 SLA；
- 法规或客户要求；
- 数据驻留与隔离；
- 突发流量风险极高；
- 单点故障不可接受。

---

## 四、技术选型优先考虑部署和维护成本

Hanov 偏好 Go，原因包括静态编译、资源占用、部署简单以及对 AI 编码工具友好。

这里不应得出“Go 是独立开发最佳语言”的结论。

更通用的选择维度是：

- 团队是否熟悉；
- 部署是否简单；
- 依赖是否稳定；
- 出错时是否容易定位；
- AI 辅助工具是否能可靠理解；
- 运行成本是否匹配业务；
- 社区与安全更新是否足够。

如果你用熟悉的 Python、Node.js、Ruby 能更快获得用户，语言理论性能可能根本不是第一瓶颈。

---

## 五、本地 AI 与云 AI 应按任务经济性分层

Hanov 对长批处理使用本地 GPU，对高质量、低延迟、前沿能力继续使用云端模型。

这个思路可以抽象为：

### 适合本地

- 大批量重复任务；
- 延迟要求不高；
- 模型能力要求固定；
- 数据不希望离开本地；
- 运行频率足以摊薄硬件成本。

### 适合云端

- 需要最新旗舰模型；
- 峰值不稳定；
- 不愿维护 GPU；
- 用户交互需要高可用；
- 模型能力差异直接影响结果。

### 混合方式

- 本地处理廉价批任务；
- 云端处理复杂推理；
- 建统一模型适配层；
- 为关键路径设置 fallback；
- 记录每类任务单位成本。

关键不是“本地一定便宜”，而是看**总拥有成本**：硬件、功耗、维护时间、利用率、失败重跑和模型质量都要计算。

---

## 六、数据库从最简单的可靠方案开始

Hanov 以 SQLite + WAL 支持自己的小型产品。

应吸收的不是“SQLite 可以替代所有数据库”，而是：

> 不要因为未来可能有高并发，就在第一天支付分布式数据库的全部复杂度。

SQLite 特别适合：

- 单节点应用；
- 内部工具；
- 低到中等写并发；
- 小型 SaaS；
- 原型和早期产品。

当出现：

- 多节点同时写；
- 高可用复制要求；
- 强横向扩展；
- 大规模分析；
- 特殊权限或数据治理；

再迁移到 PostgreSQL 或其他服务可能更合理。

重要的是提前做好：

- schema 迁移；
- 定期备份；
- 恢复演练；
- 数据导出；
- 监控磁盘和锁竞争。

---

## 七、AI 编码真正降低成本的前提是验收明确

文章中一个值得保留的实践是：给 Agent 足够详细的任务、约束和成功条件，让它持续完成测试和修复，而不是频繁人工接管。

这与 [[Agent Native团队：多Agent协作与人机分工]] 的原则一致。

一个高杠杆 AI 编码任务至少要写清：

- 要达到什么结果；
- 哪些文件或模块可改；
- 哪些不能改；
- 测试如何通过；
- 错误如何自检；
- 完成后输出什么证据。

便宜的模型调用并不自动等于低开发成本。

如果任务定义模糊，产生的返工会吞掉节省的费用。

## 八、建立“按收入升级”的基础设施策略

可以按阶段设置升级门槛：

### 阶段 A：验证

目标：最低固定成本，核心链路可用。

### 阶段 B：稳定收入

目标：强化备份、监控、安全、自动部署和故障恢复。

### 阶段 C：增长

目标：根据真实瓶颈扩容数据库、计算、缓存、队列和 CDN。

### 阶段 D：关键业务

目标：SLA、冗余、灾备、权限、审计、合规。

这样做的好处是：每一层复杂度都有业务收入或明确风险为它买单。

---

## 九、工具清单只作为候选，不作为标准答案

Awesome Indie Hacker Tools 与出海工具导航提供了大量模板、框架、数据库、支付、域名、邮件、部署、分析和 SEO 工具。

这些目录适合发现候选方案，但工具本身变化很快：

- 产品可能停运；
- 免费额度会改变；
- 定价会改变；
- 服务条款会改变；
- 原来最佳的工具可能被替代。

因此，真正长期保存的是“选择框架”：

~~~text
需要什么能力
→ 设定必须条件
→ 从目录找 2—3 个候选
→ 查官方当前文档与价格
→ 小规模试用
→ 选择迁移成本可控的一项
~~~

## 十、一个适合独立产品的成本看板

每月至少记录：

| 类别 | 关注点 |
| --- | --- |
| 基础设施 | 主机、数据库、存储、CDN |
| AI | 按模型、任务类型统计 |
| 第三方 API | 单位用户成本是否随规模失控 |
| 支付 | 手续费、退款、争议 |
| 邮件 | 交易邮件与营销邮件 |
| 分析与监控 | 是否重复购买 |
| 开发工具 | 是否真正提高吞吐 |
| 人工时间 | 最容易被忽略的真实成本 |

目标不是把每项费用压到零，而是让成本结构与收入增长保持健康关系。
