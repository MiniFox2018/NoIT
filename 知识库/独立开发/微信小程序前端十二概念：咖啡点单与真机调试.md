# 微信小程序前端十二概念：咖啡点单与真机调试

## 先分清：浏览器原型不等于原生小程序

微信原生小程序的基本分工：

| 技术 | 解决的问题 | 常见文件 |
| --- | --- | --- |
| WXML | 页面结构：容器、文字、按钮、列表 | `.wxml` |
| WXSS | 页面样式：颜色、布局、尺寸、状态 | `.wxss` |
| JS/TS | 交互与业务逻辑、计价、状态与数据处理 | `.js` 或编译后的代码 |
| JSON | 页面列表、导航标题和组件配置 | `.json` |

网页版常见的 HTML/CSS/JS 与之有概念对应，但标签、生命周期、渲染器和部分布局能力不相同。**HTML 在浏览器能运行，不代表已得到能导入微信开发者工具的原生小程序。**

本篇把十二个概念放进一条演示链路：菜单 → 饮品规格 → 购物袋 → 确认订单。示例门店为虚构的“Punk 咖啡馆”，只模拟下单，不涉及真实资金。

## 一、四页点单任务与数据流

1. **菜单页**列出美式、拿铁、摩卡；点“选规格”进入对应饮品。
2. **规格页**展示杯型中/大、冷热、单位价格；点击“加入购物袋”。
3. **购物袋**合并完全相同的规格、修改数量、计算总价；不同规格为不同条目。
4. **确认页**展示自取门店和明细，演示提交中、成功或失败的界面状态。

下述示例：拿铁中杯 24 元（内部用 2400 分存储），大杯加 4 元为 2800 分，两杯为 5600 分即 56 元。金额应使用最小货币单位或可靠的定点金额方案，避免浮点计算与客户端价格作为结算依据。

## 二、逐项理解十二个前端概念

### 01 WXML：声明页面结构

常用 `view`（容器）、`text`（文本）、`button`（按钮）。外层商品卡包住图标、名称、价格和规格入口；`class` 将结构与 WXSS 对接。例如：

```xml
<view class="drink-card">
  <text class="drink-name">{{drink.name}}</text>
  <text class="price">¥{{drink.priceText}}</text>
  <button bindtap="onChoose">选规格</button>
</view>
```

`div`、`span` 等 HTML 标签不能直接作为微信原生组件。

### 02 WXSS：布局与选中状态

`display: flex` 用于排列两个规格项，`flex: 1` 分配可用空间；`gap`、`padding`、`margin` 分别控制项间距、内边距与外边距。通过选中类名表达当前选择：

```css
.options { display: flex; gap: 8px; }
.option { flex: 1; min-width: 0; border: 1px solid #d9decf; }
.selected { background: #edf0e5; border-color: #596b38; }
```

实际 WXSS 属性可用性与渲染器/基础库有关，必须用目标环境编译检查。价格和状态不一致时不仅要查样式，还要查数据逻辑。

### 03 JavaScript / TypeScript：业务行为

点击大杯改变金额、合并购物袋条目、处理重复提交都属于业务逻辑。TypeScript 在 JS 上增加静态类型检查，却不能替代后端价格、库存和支付校验。

购物袋的合并键应至少包含**商品 ID + 杯型 + 冷热**，而不是只看“拿铁”这个显示名称。例如 `latte|large|iced` 与 `latte|medium|hot` 必须是不同条目。

### 04 JSON：页面与组件配置

```json
{
  "pages": [
    "pages/menu/menu",
    "pages/drink/drink",
    "pages/cart/cart",
    "pages/order/order"
  ],
  "window": { "navigationBarTitleText": "Punk咖啡馆" }
}
```

`pages` 里的第一项是默认启动页；路径不带扩展名。每个页面还可以有自己的配置。标准 JSON 键需双引号，不能有注释或多余的尾随逗号。

### 05 Page：页面注册与生命周期

`Page(...)` 注册页面数据及函数。导航到 `/pages/drink/drink?id=latte` 时，规格页在 `onLoad(options)` 中读取 `options.id`。要验证传入 ID 是否有效，不要直接相信路由参数。

关键生命周期：
- `onLoad`：创建页面实例时初始化一次，适合读取进入参数。
- `onShow`：页面每次显示均可触发，适合从规格页返回菜单后刷新购物袋数量。
- `onReady`：首次视图渲染完成。
- `onHide`：页面被其他页面遮住，仍可能保留。
- `onUnload`：页面移除时释放当前页面资源。

从菜单 `navigateTo` 规格页后返回，通常重新触发原菜单 `onShow` 而非 `onLoad`；`reLaunch` 会关闭原页面栈并建立新页面实例。不可把两个事件混淆。

### 06 Component：复用独立商品卡

`Component(...)` 定义复用模块；菜单页在 `usingComponents` 注册 `drink-card`。组件通过属性接收商品，通过自定义事件通知页面“选了哪个”。复用后仍需检查长标题、空描述、价格位数和按钮区域，而不能只在一款饮品上预览。

### 07 数据绑定：模板读数据

在 WXML 中用 `{{drink.name}}`、`{{priceText}}` 将数据映射到界面；`wx:for` 重复渲染商品列表，`wx:key="id"` 标识项目，`wx:if` 根据是否为空展示购物袋状态。**复杂价格计算在逻辑层完成**，不要把业务算法塞进模板表达式。

### 08 事件绑定：把点击连到处理函数

`bindtap="onSize"` 把按钮点击接到处理函数，`data-size="large"` 给它传选项；处理函数从 `event.currentTarget.dataset.size` 取值。必要时用 `catchtap` 阻止点击向父级冒泡。注意自定义 `onSize` 与平台生命周期 `onShow` 不同：前者需要自己绑定/调用，后者由系统触发。

### 09 setData：同步逻辑数据与视图

```javascript
this.setData({ size: 'large', priceText: '28.00' })
```

同一次更新提交金额和规格，才能使价格与选中颜色表达同一状态。直接改 `this.data` 不会可靠地更新视图。提交按钮的 `loading` 和 `disabled` 应绑定状态，同时在逻辑层同步阻拦重复操作，不只依赖按钮稍后变灰。

### 10 wx API：导航、提示与存储

- `wx.navigateTo`：保留当前页打开新页；
- `wx.showToast`：短提示；
- `wx.setStorageSync` / `wx.getStorageSync`：同步写入/读取本地数据；
- `wx.reLaunch`：关闭页面栈并打开新页。

本地 Storage 适合这份离线演示的购物袋。真实订单的库存、价格、支付结果和权限**必须由可信后端验证**，不能因为本地数据存在就认定支付成功。

### 11 rpx / vw：按屏幕适配

微信传统单位 `rpx` 按 750rpx 页面宽度比例换算；`vw` 表示视口宽度百分比。原文示例：375px 宽时 32rpx≈16px；430px 宽时约 18.35px。它们改善适配，但不能自动解决长文字、固定底栏、滚动或安全区域遮挡。

测试时改变模拟器屏宽，至少确认商品名、金额、选项、底部按钮和可滚动末项不会被挤掉；是否支持具体单位与 CSS 属性以当前 WXSS 规则为准。

### 12 WebView / Skyline：不同渲染方案

WebView 与 Skyline 是小程序界面的不同渲染方案；`web-view` 则是嵌网页的组件，和上述“渲染方案”不是同一个概念。不同方案在组件、样式、基础库和设备上可能存在差异；不能拿浏览器展示图代替真机验收。本示例使用默认 WebView，不包含 Skyline 专属配置。

## 三、可复用的目录与排错路线

```text
app.json
project.config.json
pages/
  menu/     menu.wxml, menu.wxss, menu.js, menu.json
  drink/    drink.wxml, drink.wxss, drink.js, drink.json
  cart/     cart.wxml, cart.wxss, cart.js, cart.json
  order/    order.wxml, order.wxss, order.js, order.json
components/
  drink-card/
utils/
  shop.js
```

问题与优先检查点：
- 商品名或价格显示错位 → WXML 标签/绑定字段。
- 选中项颜色不对 → WXSS 的 class 与状态映射。
- 选规格后金额错误 → JS 计价、规格标识、setData。
- 页面打不开 → app.json 或页面 json 的路径、大小写与文件是否存在。
- 返回购物袋数字没刷新 → `onShow` 是否重新读取持久数据。
- 相同规格没有合并或错合并 → 商品 ID + 杯型 + 冷热组成的键。
- 提交按钮重复触发 → 逻辑层互斥状态，服务端幂等保护。
- HTML 原型正常而微信页面错位 → 原生组件、渲染器、单位、安全区和实际屏宽。

## 四、微信开发者工具的六步实测

1. 从 [微信开发者工具官方下载页](https://developers.weixin.qq.com/miniprogram/dev/devtools/download.html) 选择当前系统稳定版安装，使用微信账号扫码登录。
2. 选择**原生小程序源码根目录**导入项目；应看到 `app.json` 和 `project.config.json` 等，而非只看到 HTML 预览文件。只有 HTML 时须先建立/转换原生项目。
3. 填项目名称、AppID 或可用测试号，选择实际需要的后端与开发模式。本例不用云服务，不接支付。
4. 选择“普通编译”，在模拟器运行；如失败先查控制台第一条报错并修正。
5. 实走“菜单 → 拿铁 → 大杯冰 → 购物袋两杯 → 确认”。检查单价 28 元、两杯 56 元、跳转、选中态、空态与重复提交。
6. 保存后生成预览二维码，使用有权限的手机微信扫码确认真实字体、间距、安全区、触摸区域、滚动和订单状态。

**每次修改后均需“保存 → 编译 → 预览 → 手机复核”**。推送 GitHub 只是保存源码，不等于已更新在手机上运行的小程序。原文使用的开发者工具版本 2.02.2608070 是 2026 年时点截图环境，界面入口和兼容性以后可能变化。

## 五、开发与上线边界

这是一份**前端概念与模拟订单**教程，不包含真实支付、微信商户资质、门店库存、交易安全、备案或正式上线。实际商业化应结合 [[AI辅助微信小程序商业化：从规划、开发到支付、备案与上线]] 的后端状态机、幂等、权限、备案与审查；页面信息组织可接着看 [[小程序八类任务界面：信息顺序、交互状态与结果反馈]]。

AI 可生成 WXML/WXSS/JS/JSON 初稿，但生成成功只证明写出了文件，不能取代平台编译、跨机型真机测试及交易安全审查。
