# CMP170HX本地推理服务器：显存解锁、验真与部署风险

## 本专题的边界与核心判断

NVIDIA CMP 170HX 原本面向挖矿，基于 GA100 家族架构，有高带宽 HBM 但不具备普通 A100 的完整官方数据中心支持。2026 年社区通过改动驱动和底层初始化路径，研究放开原厂受限的计算、Framebuffer 地址范围和 PCIe 配置。**“芯片可能具有某种能力”“驱动显示某容量”“内存地址可被写回”“实际能持续服务模型”是四个不同层次的事实**。任何容量展示、单次 benchmark 或商家宣传都不能自动证明生产可靠。

以下内容主要基于 [大神本人18节实操记录](https://dashen.wang/article/226) 和原入口 [X Article](https://x.com/dashen_wang/article/2090713829462458699)。按18节逐主题重组为可独立使用的技术判断和验证合同；文中实测数字仍归原操作者及社区报告，**本次没有购买显卡、刷固件、运行 CUDA/vLLM 或复现芯片解锁**。硬件低层操作可能造成不可逆损坏或系统安全降级，不建议在承载重要数据/工作的设备上直接尝试。

## 一、两个 SKU 先按 PCI ID 而非标称容量确认

| 原始版本 | 原文与项目的标识 | 文章报告的常见解锁容量 | 关键提醒 |
|---|---|---|---|
| 原厂 8GB | `10de:20c2`，16 个活动 FBPA | **64GB** | 当期社区复现相对多，但依赖非官方驱动、散热与版本适配 |
| 原厂 10GB | `10de:2082`，20 个活动 FBPA | **40GB** | 80GB 属实验性探索，不是可以稳定交付的既定规格 |

**不要把8GB→64GB与10GB→40GB映射反转。** 原文的 HBM FBPA 说明用于认识显存几何：出厂每活动 FBPA 按 512MiB 档计，16×512MiB≈8GiB、20×512MiB≈10GiB；后续某些驱动变更使可见容量按更高档计量。这不是“原厂仅用注册表藏起一块完整 A100 显存”这么简单。GB/GiB 和驱动字段存在单位差异，比较时记录单位。

### 为什么 10GB→80GB 与稳定版本不同

原文记录了使用一致的 `CFG1` 与 `LMR` 配置，再进行**dense tagged write/readback** 的 80GB 寻址实验。作者提到 77.5GiB 测试块 310/310 正确及另一轮72GiB实写读取，说明“显示 80GB 必然全是假的”这一否定过于绝对；但这类地址验证不能证明后续多 CUDA context、长时间推理、温度变化和顶端显存仍然稳定。

历史报道中的异常包括：40GB以上的访问效率下降、某些上下文后 Xid154、最后部分显存未充分测试，以及尚无面向普通用户的成熟驱动安装路线。**新用户不应按潜在80GB支付溢价，也不要把80GB当作销售承诺**。

中间容量（如 60/64/72GB）是可研究方向：作者提出保持更高层级的 FBPA 几何但通过驱动可见大小和分配器区域限制开放较小、安全的区间。这是待验证的设计猜想，未完成标准发行或独立复现前不能变成“已经支持的profile”。

## 二、WPR2 与 PMA：为何显存分配快满时才崩溃

作者追踪 [cmpunlocker PR #32](https://github.com/amoghmunikote/cmpunlocker/pull/32)：高地址区域实际承载 GSP firmware/heap 的 WPR2 保留段，却曾被 late PMA extension 当作可分配范围注册。正常使用未必触发；临近满显存、分配器碰到该区域时，可能出现 Xid31、`cudaErrorIllegalAddress`、后续 scrub 卡死和 Xid154。

修复思路是**不要把高地址受保护区域回收交给 PMA**，同时保留诊断信息。其本质是内存所有权和保留区处理错误，而不是“矿卡必定随机物理损坏”。PR 中提供了 8GB/64GB 与10GB/40GB 两个 SKU 的错误观察、修复后显存完整性和CUDA重测证据，属于**具体已报道测试**，不是任意卡/内核版本全面稳定的证明。

**时效纠错（2026-10-09）**：原作者文章写作时描述 PR #32 尚处 Open；本轮通过 [GitHub 原始 PR 数据](https://github.com/amoghmunikote/cmpunlocker/pull/32) 核对：2026-08-26 已合并到目标分支 `late-pma`，**不是**可直接推断已进入默认 `master` 的稳定发布。不能再把“PR #32 仍 Open”当成当前项目结论。

## 三、验证工具本身的假阳性：逐卡检查才算通过

[PR #33](https://github.com/amoghmunikote/cmpunlocker/pull/33) 讨论的 `verify.sh` 曾可能依赖安装时记录的GPU清单，新增卡未纳入验证却仍报告成功；此外普通用户没有读取 `dmesg` 的权限时，脚本可能把“读取失败”误当“无错误日志”。**验证工具没检查到 ≠ 被检查对象没故障**。

2026-10-09 GitHub 核对 PR #33 也已在 **2026-08-26 合并至 `kirea` 分支**；仍需看主线实际包含的 commit 与已安装版本，不能只看“Merged”按钮就认为已发布。

多卡的可信验收至少有下面七层：

1. 逐张列出 PCI ID 与物理插槽/设备顺序，包括后加的卡；验证工具枚举数量要和 OS 一致。
2. 分别核对驱动报告容量、`CFG1` / `LMR` 与期望 SKU，记录驱动构建/内核版本。
3. **地址折叠测试**：高地址与低地址放不同标记，确认彼此不会别名覆盖。
4. **真实 CUDA**：逐区 allocate/write/read/free；不止调用 nvidia-smi。
5. **高占用边界**：接近可分配显存上限运行，验证 reserved region 不被错误使用。
6. **日志可信度**：检查 Xid、GSP、scrub 等内核事件；读取权限失败必须算“不可判定”，不是通过。
7. **热态长时间 serving**：跑满预期并发和上下文，不仅短时显存测试。多卡必须按卡存储结果。

## 四、性能：prefill、decode、总吞吐和稳定性各是不同指标

文章提供多个环境（Qwen不同版本、INT8 W8A8、KV精度、MTP、vLLM、SGLang、USB4 eGPU）上的性能记录。不同硬件主机、量化版本、prefill/decode、批处理、输入输出长度**不能直接横比**，尤其不能据“8GB解锁64GB比10GB解锁40GB的汇总吞吐更高”推断两块硬件只差显存容量。

记录一条可以复现的 benchmark 至少包含：

| 类型 | 必留字段 | 为什么 |
|---|---|---|
| 硬件 | PCI ID、解锁容量、主机、CPU/RAM、PCIe Gen与宽度、电源/散热 | 排除硬件差异 |
| 软件 | GPU驱动与patch SHA、内核、CUDA、vLLM/SGLang、模型 revision | 同名模型不同版本可能有巨大差异 |
| 模型与精度 | 权重/量化、KV cache、最大上下文、是否MTP、张量并行 | token/s 可变原因 |
| 请求负载 | 输入/输出 token 分布、并发数、请求量、warmup | 单用户速度不能推导吞吐 |
| 核心指标 | TTFT、prefill tok/s、decode tok/s、aggregate tok/s、P50/P95、失败/重试 | 用户体验与系统容量 |
| 可靠性 | 总时长、每卡Xid、静默错误验证、HBM/core温度、功耗、降频 | 避免“短时跑分好看但持续服务不稳定” |

原文引用过单卡约70 tok/s、其他人vLLM约95—103 tok/s decode、SGLang聚合约200—380 tok/s，以及170tune在长时间运行下的更高并发数据。以上数字**只作为历史案例**，不能当作这张卡在任意模型上的官方规格或硬件采购保证。

### 稳定性最危险的是静默算错

即使程序返回 exit 0、没出现 Xid，也可能存在静默显存损坏。研究工具 [170tune](https://github.com/cachenetics/170tune)（2026-10-09 已核验真实 GitHub 仓库，具体调优参数要按本卡与使用中的驱动/解锁分支独立 qualification）主张全VRAM写入图样/回读、bit-exact GEMM、热态资格验证和真实 serving 压测。**若无法给出可信的官方/项目原仓库路径，绝不能凭工具名字编造代码下载地址或脚本命令。**

部署前要对比不同温度下同一测试集的结果，保留摘要哈希、负载、错误和物理条件。只展示某次“31分钟0失败”仍不能证明24小时或长期环境稳定，尤其是非官方驱动。

## 五、PCIe 与散热：所谓“便宜大显存”的隐性成本

- **PCIe**：Gen1→Gen2 是代际，`x4`→`x16` 是物理lane宽度。通过驱动提升代际与硬件补元件提升实际位宽不是一回事；多GPU张量并行的跨卡通信可能被窄带宽拖垮。更合适的候选是“每卡独立承载一个模型/服务”，但也要先核吞吐和需求。
- **被动散热**：面向服务器强风道的卡在普通PC机箱中可能过热，不能只看GPU核心温度，还要看HBM、风量、供电和高负载持续时长。冷态测试通过不意味着热态不会计算错误。
- **安全与支持**：非官方驱动补丁、Secure Boot兼容性、ECC/稳定性和内核更新持续风险；文章特别指出不是官方A100、NVLink与部分生产功能不完整，不能当同级产品销售。
- **费用与收益**：二手价格会随社区解锁热度波动；原文提到由约250美元上涨至1000美元以上的报道并非今日市场报价。真实TCO还包括配套机箱/风扇、供电、运维、驱动维护、卡损风险、保修、使用时间和替代硬件可用性。

## 六、采购和上线前的可执行决策门

**资格门1：来源与型号**。有真实 PCI ID 和硬件照片、商家退货条件；不得只根据“显示64/80GB”的截图付款。

**资格门2：软件与版本**。目标 OS/内核支持情况、driver patch 的真实 SHA、是否纳入 PR #32/#33 的修复、可回滚系统快照；不在保存重要数据的机器上用未知驱动。

**资格门3：显存可靠性**。逐卡范围与地址别名检测、高占用/热态 CUDA 真实读写、内核日志权限、无静默数据损坏。

**资格门4：模型业务**。使用自己的真实模型/量化/上下文/并发和 SLA，核算单位有效请求的能耗、平均与尾延迟；可以被其他二手/新卡合理替代时必须重新比价。

**资格门5：长期运营**。散热、监控、备件、坏卡隔离、备份、恢复计划、维护知识及退出成本。测试无故障不意味着生产可以移除观察与告警。

明确**不建议**：把 10GB→80GB 当作确定性商品、为了购买低价二手卡而关闭所有系统安全策略、将未经复核的 CUDA 驱动安装到工作主机、用短时一张截图承诺商业算力。
