# AI产品经理全流程：项目事实、需求决策与交付闭环

AI 产品经理的核心能力不是快速生成一份漂亮文档，而是让 Agent 在**真实且不断变化的项目事实**上完成研究、分析、设计、交付和复盘，同时保留人的责任判断。

## 一、初始化：把项目变成可持续更新的上下文

采用「原始材料 → 产品现状与规划 → 需求池 → 单项需求 → 版本计划 → 验收与复盘」的路径组织 Markdown。首先收集已上线功能、历史 PRD、截图、设计规范、访谈、评审结论；分别标明**已确认事实、待验证假设、未来提案**，不要把聊天讨论当作上线事实。

每个需求给唯一编号、状态、来源、负责人、决策日期及关联版本。每一类事实应有唯一维护位置；图表、PPT、PDF 作为交付物，不取代事实源。正式状态修改与高风险写入由人确认。

## 二、市场分析：AI 扩大线索，人核验事实

多模型结果只用于扩大搜索覆盖，不能以「多个模型给出同一数字」代替独立证据。优先官方公告、财报、权威统计与原始报告；同一指标记录口径、时间、地区、统计方法和来源。拿不到可信出处时写「未核实」，不得精确编造用户量。

## 三、调研：补足公开网页以外的内部信息

客户访谈、业务目标、领导取舍、研发约束、历史失败、真实用户反馈经常不在公共互联网上。会议纪要记录**事实、观点、尚未决定的事项**；对没有授权的公司数据不上传外部模型。AI 只能基于获得的材料分析，而不能推断公司内部真实优先级。

## 四、需求分析：先做加法，再主动做减法

先用 AI 枚举正常流程、边界、异常、依赖、成本和风险；然后由产品负责人按价值/频率/代价删掉低收益复杂度。每个正式保留的决策要能回答「为什么做、为什么现在做、为什么不选其他方案」。不让 AI 擅自扩大需求，也不把技术方案直接当业务结论。

## 五、原型：约束先于生成

把已有设计系统、UI 组件、关键页面、尺寸、交互规范、可访问性和状态需求交给 Agent，再生成 HTML 等原型。需要验证空态、加载、错误、权限和移动端等真实状态；视觉统一和任务完成情况都属于验收条件。没有设计系统时先确立少量参考和简洁规则，避免每个页面重造风格。

## 六、PRD：同时对人和 Agent 可读

人阅读的 PRD 保证业务背景、用户场景、主流程、界面状态、规则、边界、验收标准清楚；交接给研发或测试 Agent 的 Markdown 需要更完整的字段、编号、数据字典与决策上下文。不能只用截屏代替可复查的需求逻辑。

建议最低字段：**需求 ID、问题、用户、业务目标、当前事实、方案、非目标、交互与异常、依赖、验收用例、来源、版本、未决事项**。

## 七、评审与研发：变更写回唯一事实源

评审结束不只更新最终方案，还记录「会议、时间、参与角色、原因、替代方案、影响」。例如从 A 变为 B，应同步 PRD、验收用例、任务状态和相关设计，而不只修改代码；保留废弃方案的决策记录便于以后追溯。

## 八、测试上线：把需求变为可执行的验收条件

根据 PRD 自动生成测试用例与操作步骤，浏览器自动化/Computer Use 可以辅助验证主流程、跳转、表单、不同状态以及回归影响。但界面好不好、是否真正解决用户问题、是否达成目标，仍须产品负责人判断。不能把 Agent 显示「测试通过」当成证据，必须保存日志和可复查结果。

## 九、运营反馈：构成下一版本输入

反馈按照「来自谁 → 发生何时 → 复现步骤 → 影响 → 支持证据 → 当前状态 → 归属需求」记录。将线上故障、延期项、需求变更和用户访谈持续写回项目，再由 Agent 形成候选版本清单；人负责最终优先级和取舍。

## 一页协作检查清单

- 项目事实是否有来源、时间、当前状态和事实拥有者？
- 本次变更的边界、非目标、需要人批准的步骤是否写明？
- 生成的功能、设计、PRD 是否满足当前版本而不是历史版本？
- 需求评审之后，原型、PRD、研发任务和测试是否同步更新？
- 上线后反馈是否能回溯到原始需求与决策理由？
- AI 有没有把推断伪装成公司事实，或把可选功能变成「必须」？

三条原则：**上下文充分、主动约束、先判断再加速**。详见 [[产品早期验证：先验证价值，再打磨细节]] 和 [[工程Agent工作流：从任务边界到可审查交付]]。

## 十、把产品全流程变成可执行的项目工作空间

本节承接 [奔跑的大毛腿《产品项目初始化 Prompt》](https://x.com/run_maotui/status/2100156767137415210)。与前九节的产品判断相比，这份增量的重点是**项目脚手架的事实归属、状态机、来源登记、Agent 写入规则与初始化验收**。它是**创建新产品工作空间时的候选方案**，不是要求对已有 NoIT 仓库立即改名、迁移目录或创建大量空文件。

### 10.1 空项目的工作流目录及职责边界

| 工作区 | 存储对象 | 不应该存什么 |
|---|---|---|
| \`00-rules/\` | 唯一事实源、命名约定、阶段门槛、Agent 协作规则 | 当前需求状态的第二份副本 |
| \`01-inputs/\` | 原始讨论、调研记录、截图、材料版本和来源登记 | 未审定的“正式产品结论” |
| \`02-product/\` | 当前产品能力、术语、目标用户、平台和技术约束 | 用户访谈原稿、未经验证的未来计划 |
| \`03-planning/\` | 问题空间、模块地图、备选方案、取舍理由 | 已冻结的版本交付范围 |
| \`04-requirement-pool/\` | 每个候选需求的唯一 ID、**当前状态**、优先级与负责人 | PRD 正文、互相冲突的状态备份 |
| \`05-requirements/\` | 各需求的场景、PRD、原型、依赖、边界状态和测试用例 | 与其他需求混写的共享状态主表 |
| \`06-versions/\` | 版本目标、承诺的需求 ID 列表、依赖与里程碑 | 随手复制一遍整个 PRD 或需求池 |
| \`07-reviews/\` | 评审、发布证据、验收结论、复盘和例外签批 | 只有“已完成”没有证据的状态描述 |
| \`90-assets/\` | 共享设计素材、原型截图、演示与模板 | 私密密钥、未授权的第三方素材 |
| \`99-archive/\` | 已废弃版本与经过确认的关闭记录 | 仍在正式维护的事实、仅因旧就随意丢弃的材料 |

编号仅用于自然排序；如果一个团队已有 Jira、Linear、飞书或既定仓库结构，就应**映射既有唯一事实源**，不把上述目录强制复制一份形成双系统。特别是已有代码仓库不得在不清楚状态时直接批量移动文件。

### 10.2 四类规则应该解决的真实问题

- **命名与结构规则** \`naming-and-structure.md\`：每个目录是什么、什么不得入内；需求 ID 如 \`req-0001\`，来源 ID 如 \`SRC-0001\`，版本 ID 如 \`v0.3\`。编号必须唯一、可搜索，重命名后保留旧 ID 追溯；不强制用户文件都使用英文名。
- **唯一事实源** \`source-of-truth.md\`：把“当前产品支持什么”归在产品事实，把“需求当前进度”归在需求池，把“版本承诺范围”归在版本计划；其他文件通过 ID 和相对路径引用，不另记独立主值。来源变化时指出需联动的消费方，但不让 Agent 未经授权静默改掉审批结论。
- **状态与门槛** \`status-and-gates.md\`：声明谁可以提议/审批/推进/回退状态、每次推进必须附什么证据；有状态名称不代表具备批准权。
- **工作流规则** \`product-workflow.md\`：输入登记→产品规划→需求池→单需求工作包→原型/PRD→版本承诺→开发与验收→真实上线→复盘。每个阶段可由 Agent 产出草稿，但必须保留“已观察／推断／待确认／未覆盖”的证据等级。

根目录 \`README.md\` 只给出工作空间目的、当前阶段和进入上述区域的导航。根目录 \`AGENTS.md\` 只写规则索引、允许/禁止动作和完成标准，具体流程只在相应规则文件维护。即使改用 Claude Code，也不需要将全部细节复制进 \`CLAUDE.md\` 形成第三套互相矛盾的规则。

### 10.3 需求状态机：关口比状态名称重要

完整流程可以是：

\`\`\`text
candidate → collecting → analyzing → defined → reviewing
→ approved → developing → validating → released → closed
\`\`\`

初创产品可以只用：

\`\`\`text
candidate → analyzing → defined → approved → released → closed
\`\`\`

无论选哪种，以下条件不能缺失。

| 流转 | 需要的输入与确认 | 禁止的捷径 |
|---|---|---|
| 新输入 → candidate | 来源 ID、问题描述、登记人和日期；当前只是候选 | 截图、口头讨论直接标为“已批准” |
| analyzing → defined | 用户/场景、可核验事实、范围、非目标、依赖和主要不确定性 | AI 填空替代访谈与业务判断 |
| reviewing → approved | 负责人/签批记录、变更摘要、原型或 PRD、验收标准 | 无人确认即写入正式状态 |
| approved → developing | 已明确的版本范围、开发入口和责任人 | 把开发动作等同于业务批准 |
| validating → released | 目标环境部署记录、可复查测试、上线观察/回滚点 | 构建成功、PR 合并、Agent 说完成就当已上线 |
| released → closed | 验收通过、遗留问题归档、实际运营反馈与复盘 | 未观察用户使用就宣称商业结果达成 |

如果批准后实质改变范围，应生成变更记录，转回 \`reviewing\` 或明确走变更审批；如果紧急修复需要例外，应另记例外签批、影响与补审日期，不靠秘密状态字段掩盖。

**状态唯一维护在需求池**；PRD 和版本页可展示引用或生成视图，但不能人工维护另一份不同的状态文本。为了防止陈旧，字段旁可保留版本号/时间戳；产品负责人具有最终签批权。

### 10.4 来源登记、需求池及版本承诺的最小数据合同

来源登记（仅展示字段和空模板，不含假造业务记录）：

\`\`\`text
来源：SRC-XXXX
取得时间：
材料路径或受控系统链接：
提交者／来源：
证据身份：已观察 / 推断 / 待确认 / 未覆盖
允许引用或使用的范围：
替代或更正前版本的记录：
\`\`\`

需求池应稳定包含：\`REQ-ID\`、名称、源 \`SRC-ID\`、问题/用户、模块、当前状态、优先级及依据、负责人、工作包链接、候选版本、前置依赖、最后审核时间。

一个需求工作包至少要能脱离聊天独立回答：

1. **问题与价值**：谁在什么情境遇到什么问题，有什么可复查证据；不只是“希望加一个功能”。
2. **主路径与分支**：入口、用户动作、系统状态、成功反馈、取消/失败/权限不足、数据读写和可能的竞态条件。
3. **规则与边界**：必须做到、明确不做、数据口径、技术/合规/无障碍约束和外部依赖。
4. **交付方式**：原型路径、PRD 唯一主稿、验收用例、责任人和版本引用。
5. **签批与变更**：决定日期、变更理由、替代方案、批准人及未决事项。

版本范围表**只引用已批准的需求 ID**，记录纳入原因、预计成本、前置依赖和验收责任；追加需求也先更新正式决策，再同步版本承诺。不因 PRD 自动扩写而自动扩增版本范围。

### 10.5 初始化的安全执行与验收

建议让 Agent 分成四轮，避免“一句话就批量覆盖整个项目”。

1. **只读盘点**：先检视已有目录、README、AGENTS.md、产品事实与 Git 状态，报告哪些材料已经存在及如何映射；有未提交修改时不能抹掉。
2. **提出脚手架差异计划**：列出拟创建文件、拟引用既有事实源、需要明确权限的动作和潜在重名路径；并由负责人批准。
3. **仅创建已授权的最小骨架**：规则文件、README 入口、来源登记和空需求池；必要时分支提交。不要先产几十篇内容空泛的模板，也不要把历史材料改写为已批准需求。
4. **试运行一条真实需求**：输入登记→候选需求→完整定义→审批→版本决定→测试证据→复盘。每一步人工或自动生成状态必须按权限执行；核对链接和唯一事实、检查是否泄露秘密，再决定扩充模板。

**项目初始化的通过标准**不仅是“十个目录建好了”，还包括：新成员能从 README 找到资料；一个来源能追到需求；一个批准需求能追到版本与验收；不存在互相冲突的状态；Agent 知道何时只能建议、何时须用户批准；失败能恢复原文件。

### 10.6 可迁移的最小任务合同（由本文整合重写）

\`\`\`text
目标：为一个全新的产品项目建立可长期维护的 AI 协作骨架。
第一步：只读检查当前文件和 Git 状态，识别已有事实源。
第二步：提出目录映射、规则文件、输入登记表、需求池和 README/AGENTS.md 清单。
第三步：标记无法确认的现状和需要负责人批准的事项，不把猜测改成批准事实。
第四步：获得授权后，按最小可用结构新增文件，不删除、不覆盖既有内容。
第五步：以一条无敏感信息的虚拟需求检验登记、评审、版本引用与验收流程。
交付：文件差异、唯一事实源映射、通过/失败检查、仍待确认事项与回滚方法。
禁止：写入 API Key / Cookie / 密码，发布客户内部材料，未经批准推进正式状态或执行上线。
\`\`\`

关联既有的 [[工程Agent工作流：从任务边界到可审查交付]]：工程 Agent 负责如何在授权边界内可靠操作，产品工作空间负责**哪些事实、决策与版本承诺可以被操作**。项目初始化并不意味着这些状态真的已创建、审批或上线。
