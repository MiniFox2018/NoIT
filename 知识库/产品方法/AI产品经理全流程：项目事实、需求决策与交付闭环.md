# AI产品经理全流程：项目事实、需求决策与交付闭环

AI 产品经理的核心能力不是快速生成一份漂亮文档，而是让 Agent 在**真实且不断变化的项目事实**上完成研究、分析、设计、交付和复盘，同时保留人的责任判断。

## 一、初始化：把项目变成可持续更新的上下文

采用「原始材料 → 产品现状与规划 → 需求池 → 单项需求 → 版本计划 → 验收与复盘」的路径组织 Markdown。首先收集已上线功能、历史 PRD、截图、设计规范、访谈、评审结论；分别标明**已确认事实、待验证假设、未来提案**，不要把聊天讨论当作上线事实。

每个需求给唯一编号、状态、来源、负责人、决策日期及关联版本。每一类事实应有唯一维护位置；图表、PPT、PDF 作为交付物，不取代事实源。正式状态修改与高风险写入由人确认。

## 二、市场分析：AI 扩大线索，人核验事实

多模型结果只用于扩大搜索覆盖，不能以「多个模型给出同一数字」代替独立证据。优先官方公告、财报、权威统计与原始报告；同一指标记录口径、时间、地区、统计方法和来源。拿不到可信出处时写「未核实」，不得精确编造用户量。

## 三、调研：补足公开网页以外的内部信息

客户访谈、业务目标、领导取舍、研发约束、历史失败、真实用户反馈经常不在公共互联网上。会议纪要记录**事实、观点、尚未决定的事项**；对没有授权的公司数据不上传外部模型。AI 只能基于获得的材料分析，而不能推断公司内部真实优先级。

## 四、需求分析：先做加法，再主动做减法

先用 AI 枚举正常流程、边界、异常、依赖、成本和风险；然后由产品负责人按价值/频率/代价删掉低收益复杂度。每个正式保留的决策要能回答「为什么做、为什么现在做、为什么不选其他方案」。不让 AI 擅自扩大需求，也不把技术方案直接当业务结论。

## 五、原型：约束先于生成

把已有设计系统、UI 组件、关键页面、尺寸、交互规范、可访问性和状态需求交给 Agent，再生成 HTML 等原型。需要验证空态、加载、错误、权限和移动端等真实状态；视觉统一和任务完成情况都属于验收条件。没有设计系统时先确立少量参考和简洁规则，避免每个页面重造风格。

## 六、PRD：同时对人和 Agent 可读

人阅读的 PRD 保证业务背景、用户场景、主流程、界面状态、规则、边界、验收标准清楚；交接给研发或测试 Agent 的 Markdown 需要更完整的字段、编号、数据字典与决策上下文。不能只用截屏代替可复查的需求逻辑。

建议最低字段：**需求 ID、问题、用户、业务目标、当前事实、方案、非目标、交互与异常、依赖、验收用例、来源、版本、未决事项**。

## 七、评审与研发：变更写回唯一事实源

评审结束不只更新最终方案，还记录「会议、时间、参与角色、原因、替代方案、影响」。例如从 A 变为 B，应同步 PRD、验收用例、任务状态和相关设计，而不只修改代码；保留废弃方案的决策记录便于以后追溯。

## 八、测试上线：把需求变为可执行的验收条件

根据 PRD 自动生成测试用例与操作步骤，浏览器自动化/Computer Use 可以辅助验证主流程、跳转、表单、不同状态以及回归影响。但界面好不好、是否真正解决用户问题、是否达成目标，仍须产品负责人判断。不能把 Agent 显示「测试通过」当成证据，必须保存日志和可复查结果。

## 九、运营反馈：构成下一版本输入

反馈按照「来自谁 → 发生何时 → 复现步骤 → 影响 → 支持证据 → 当前状态 → 归属需求」记录。将线上故障、延期项、需求变更和用户访谈持续写回项目，再由 Agent 形成候选版本清单；人负责最终优先级和取舍。

## 一页协作检查清单

- 项目事实是否有来源、时间、当前状态和事实拥有者？
- 本次变更的边界、非目标、需要人批准的步骤是否写明？
- 生成的功能、设计、PRD 是否满足当前版本而不是历史版本？
- 需求评审之后，原型、PRD、研发任务和测试是否同步更新？
- 上线后反馈是否能回溯到原始需求与决策理由？
- AI 有没有把推断伪装成公司事实，或把可选功能变成「必须」？
